# NTE 比赛 · 赛事平台

自动分组 / 积分结算 / 实时排行 / 直播推流的一体化赛事平台，
**不限定具体项目**——排球、羽球、卡牌、电竞等对抗赛都能直接用。
后端 FastAPI + WebSocket；前端是**无依赖的原生 ESM 单页应用**（没有打包器，
连样式也是手写的 CSS），部署时不需要构建步骤。

## 快速开始

```bash
# 安装依赖（uv 会自动创建虚拟环境）
uv sync

# 启动服务（默认 0.0.0.0:8000）
uv run python -m app

# 换个端口 / 只监听本机
uv run python -m app --port 8123
uv run python -m app --host 127.0.0.1 -p 8123
# 等价的环境变量写法：NTE_PORT=8123（命令行参数优先）
```

浏览器打开 <http://127.0.0.1:8000> 即可。

`uv run python -m app --help` 是**分组的彩色帮助**（启动 / 自检 / 本机维护 / 环境变量 /
常见操作 / 配套脚本 各一组，命令名高亮、说明折行对齐；列宽按终端**显示宽度**算，
中文与英文混排也不会歪），实现见 `app/console.py`：

* **不是终端就不上色**：管道、重定向到文件、CI 日志里一个转义码都不会有
  （`python -m app --help > help.txt` 拿到的是干净的纯文本，测试也靠这个保证输出可断言）；
* 设了 `NO_COLOR`（通行约定）或 `NTE_NO_COLOR` 就一定不上色；
* Windows 老控制台会自动按一下 `SetConsoleMode` 的 VT 位（拿不到控制台也只是没颜色）；
* 帮助文本里**没有 Markdown 记号**：终端不会把 `**加粗**` 渲染成粗体，只会原样印出星号，
  所以强调靠用词、高亮靠颜色。

也可以用容器跑（数据挂在卷上，容器重建不丢）：

```bash
docker compose up -d
docker compose logs -f nte      # 首次启动的服务器管理员登录密钥只在这里出现一次
```

首次启动会自动创建 SQLite 数据库 `config/nte.sqlite3`，里面只有一个空的「首届赛事」——
**不带任何示例选手、队伍或比赛**，届状态是「筹备中」，全部等你自己录。第一次上手的顺序：

1. 「服务器 → 成员管理」里把参赛的人加成成员（**跨届共享**，姓名 / QQ / 游戏 UUID 录一次就够）；
   也可以直接在「本届参与名单 → 从成员列表选择」里勾人：本届还没有档案的会**按成员资料自动建好**，
   不用先去登记一遍（要临时客串、没有账号的人，才用「选手」页的「新增选手」）；
2. 「本届参与名单」勾选本届真正上场的人（候选就是**成员列表**；取消勾选只移出名单，档案留着）；
3. 锦标赛制再「随机组队」；然后「生成赛程」；
4. 确认无误后点「开始比赛」（赛制与名单随之锁定，之后仍可录分、安排替补与查看直播地址）；
5. 要直播的话：在「服务器管理 → 直播配置」填自己那台媒体服务器的地址（**出厂是空的**），
   并给有推流需求的成员设置「推流 ID」与 Bearer 令牌。

> 主页上有一张**三步开赛引导卡**（只给有权限的人看），缺哪步就提示哪步，
> 全部配好后自己消失——新装站点不用对着空页面猜。

> **服务器管理员**（全局有且只有一个）由程序启动时自检：若库里还没有，会自动创建一个
> 并**在控制台打印随机登录密钥**（仅此一次），登录走的就是这把成员密钥（见「登录与权限」）。
> 成员、届次、直播封禁、自定义 HTML 都在 `/admin`（顶栏右上角「管理」，仅管理员可见）；
> 任何登录用户（**包括服务器管理员自己**）都在 `/user` 改自己的资料、注销登录。
> 详见下文「成员、权限与服务器管理」。

> 早期版本曾把一份示例名单写进新库。若库里的名单**仍是那 10 位原样未动**、
> 且没有任何比赛 / 队伍 / 参与名单，启动时会自动清掉并在日志里记一笔；
> 一旦你改过名字或已经用它排过赛，一律不动，交给管理员自己删。

## 登录与权限

**只有一套凭据：成员密钥。** 登录（`POST /api/auth`）只认成员密钥——命中了哪位成员，
会话就带上他的 `uid` 与 `permission`，**能改什么完全由身份决定**。服务器管理员也只是
「权限最高的成员」，用他自己的成员密钥登录，和别人一样。

| 身份 | 能做什么 |
| --- | --- |
| **赛事管理员**（`event_admin`） | 创建赛事；全权管理 / 删除**自己创建的**届；不能增减成员 |
| **服务器管理员**（`server_admin`） | 全部权限：成员管理、任意届次、全局直播封禁、自定义 HTML、频道与频道公告；**本身也是一位成员**，有自己的 `/user` 页 |

> **没有「主管理 KEY」这回事了。** 早期版本有一套按届存储、换来的却是全局会话的
> 主管理 KEY（出厂值 `NTE-ADMIN`），任何一届遗留的它都等于一把万能钥匙——那套凭据
> 已整体退休：老 KEY 一律失效，旧库里那张 `event_admin` 表会在启动时被删掉。
> 现在**登录与管理都只看成员身份**。

### 服务器管理员的密钥从哪来

首次启动时，自检发现没有服务器管理员就会自动创建一位，并**只在那一次**把密钥打进
日志（明文只出现这一次，库里存的是加盐哈希）：

```
====================================================================
未检测到服务器管理员，已自动创建：服务器管理员
登录密钥（仅此一次显示，请立即保存）：V2FP-THS5-RPKJ
在 /admin（服务器管理）或 /user（个人）用该密钥登录；忘记可在成员管理里轮换。
====================================================================
```

之后每次启动只打印一行登录方式提示。全站**有且只有一个**服务器管理员，现在的守卫是**三重锁**：
不能把别的成员设为服务器管理员、不能把唯一的管理员降级 / 停用、也不能删除他
（对应 `app/members.py` 里三处 400）。

> 因此**界面上没有"交接"路径**：换人用命令行（先停服）——
>
> ```bash
> # 交互式：列出成员 → 选接任者 → 选「删除旧账号 / 降级」→ 确认
> uv run python -m app --transfer-admin
>
> # 也可以直接指定（目标写 uid / QQ / 名字片段）
> uv run python -m app --transfer-admin 10002 --delete-old   # --keep-old 则降级（默认）
> uv run python -m app --transfer-admin 10002 --key 我的新密钥
> ```
>
> 它会一次做完三件事：把接任者升为服务器管理员、**给 TA 派发新密钥**（只打印一次）、
> 旧管理员**删除或降级**。删除时他创办的届会变成「无主」（由服务器管理员接管），
> **比赛内容不受影响**；重启后所有在线会话作废。
>
> 实在要用数据库改（CLI 也跑不起来时）：停服后
> `UPDATE members SET permission='event_admin' WHERE permission='server_admin';`
> 再 `UPDATE members SET permission='server_admin' WHERE uid='目标 uid';`，然后重启。
> 注意：编辑表单里那个「服务器管理员（有且只有一个）」选项，对**别人**是死路——
> 选了会被接口拒掉（它只用于"自己保持是自己"）。

### 忘记密钥怎么办

凭据就是「能访问服务器上的数据库文件」，因此有服务器权限的人可在本机重置：

```bash
# 1) 先停止服务（重要：运行中的实例内存里仍是旧凭据）
# 2) 重置（省略新密钥则随机生成一个易读的，如 V2FP-THS5-RPKJ）
uv run python -m app --reset-key

# 指定新密钥
uv run python -m app --reset-key 我的新密钥

# 3) 重新启动服务，用打印出的新密钥登录（/admin 或 /user）
```

重置写的是**加盐哈希**、不保留明文；若服务仍在运行，命令会明确提示先停服。
登录页也贴了这一条命令，忘了不需要翻文档。

> 它重置的是**服务器管理员成员**的密钥，与届次无关（早期版本可以用 `-e e002`
> 按届重置，那个参数已随主管理 KEY 一起移除）。

## 成员、权限与服务器管理

除了「赛事」这条主线，平台还有一套**全局账号**体系：成员、权限、成员密钥与推流令牌、
直播封禁、自定义 HTML、以及统一管理历届比赛的服务器管理页。

### 三种权限

| 权限 | 能做什么 |
| --- | --- |
| **成员**（`member`） | 在 `/user` 修改自己的资料、直播间名字，轮换自己的密钥 / 令牌；不能用任何管理入口 |
| **赛事管理员**（`event_admin`） | 创建赛事，并**全权管理 / 删除自己创建的**赛事（用 `/<届>/manage` 那套赛事路由）；不能增减或修改成员 |
| **服务器管理员**（`server_admin`） | 全部权限：成员管理、任意届次、全局直播封禁与解除、自定义 HTML、**频道与频道公告（全局资源）**；**本身也是一位成员**，同样有自己的 `/user` 页 |

**服务器管理员全局有且只有一个**：程序启动时自检，缺失则自动创建「服务器管理员」账号并
把**随机密钥打印到启动日志**（仅此一次，请立即保存）；若检测到多个，只保留最早创建的那个，
其余降级为赛事管理员。他**就是一位普通成员**（有 `uid`、头像、推流 ID、自己的密钥与令牌），
只是权限最高——所以「管理」与「我的」这两个入口对他都可用，也**不能被停用 / 降级 / 删除**。

> **顶栏右上角**是与赛事无关的入口（页签里不再单列）：
>
> | 界面元素 | 出现条件 | 去哪 |
> | --- | --- | --- |
> | **「登录」按钮** | **未登录时** | `/user` 的登录门 |
> | **「头像 + 用户名」** | 登录后（认得出「你是谁」） | 自己的 `/user` |
> | **「管理」按钮** | **仅服务器管理员** | `/admin`（服务器管理） |
>
> 也就是说**没登录时右上角只有一个「登录」**：不会出现挂着的「管理」按钮或「未登录」牌子。
>
> 这些入口都**不随届次切换**；`/admin` 与 `/user` 直接输入地址照样能进
> （刷新 / 收藏 / 分享都落得住，只是没权限时页内会给出对应的提示 / 登录门）。

### 成员（全局账号）

成员是本站的账号，**跨届共享**，与「选手名单」的区别是它不带任何比赛信息：

| 字段 | 说明 |
| --- | --- |
| `uid` | **网站用户 UUID**（创建时自动生成、全局唯一、不可修改），用它区分用户 |
| `name` / `avatar` / `qq` | 展示信息；QQ 仅服务端用于取头像（走 `/api/avatar/m/<uid>`） |
| `gameUuid` | 游戏内 UUID |
| `streamId` | **推流 ID**（全局唯一，也是他在媒体服务器上的推流路径） |
| `roomTitle` | 直播间名字（成员自己在 `/user` 改） |
| `permission` | 权限 |
| `secretKey` / `bearerToken` | 登录密钥 / 推流 Bearer 令牌（**只由服务端随机生成**） |

**密钥与令牌的存储规则**：两者都只由服务端随机生成，明文**只在生成 / 轮换的那一次**回给
前端一次；之后一律以**加盐哈希**保存，任何接口都取不回明文，只能**轮换**——轮换后旧值
立即失效（换密钥还会注销该成员的全部在线会话）；两者都**全局唯一**。

### 凭据是怎么存的（加盐）

| 凭据 | 熵 | 存储形式 |
| --- | --- | --- |
| 成员登录密钥 | ≈192 位随机 | `hmac_sha256$<随机盐>$<摘要>` |
| Bearer 推流令牌 | ≈256 位随机 | 同上 |

* **逐条随机盐**：两条相同的凭据也会得到完全不同的哈希，无法交叉比对 / 彩虹表反查；
* 校验一律**常量时间比较**（并且按 UTF-8 字节比——否则用户输入中文 / emoji 时
  `hmac.compare_digest` 会直接抛异常）；
* 高熵凭据（随机生成的密钥 / 令牌）**不套迭代**：它们本来就是 192~256 位随机串，没有
  「弱口令」可猜，迭代只会让每次推流鉴权白烧十几毫秒；
* 哈希串里自带**盐与参数**，且随数据库 / 备份一起走——**导出、备份、还原到别的机器
  都不影响校验**；
* **老库平滑升级**：历史上写的是无盐 `sha256`，仍能继续校验（管理端会在成员卡上标
  「凭据待升级」，并在成员面板顶部提示还有几位待轮换）；服务端拿不到明文、无法自动升级，
  **轮换一次**即写成加盐格式。

> 凭据**任何情况下都不进「导出配置」的 JSON**，也不会出现在公开状态里——只有
> `hasKey` / `hasBearer` 这类布尔会下发。

### 登录用哪把钥匙

`POST /api/auth` **只接受成员密钥**：命中某位成员即可登录，会话带上他的 `uid` 与
`permission`。服务器管理员用他自己的成员密钥登录（见上一节）；此外「本机直连免登录」
（`localhost` / `127.0.0.1`，可在登录限制里关闭）会直接签发服务器管理员会话。

**管理只认身份**：进了「赛事管理」能改哪几届，完全由会话里的身份决定——服务器管理员
可管全部届，赛事管理员只能管**自己举办的**届。打开一届不是自己办的赛事时，页面会直接
写明「这一届由 XXX 举办」并给出回主页 / 看自己的届的去路，而不是等你点保存之后收到 403。

前端会记住身份（`GET /api/auth/check` 回传 `permission / uid / name`），并据此决定顶栏的
「管理」按钮、右上角「头像 + 用户名」与「赛事管理」页签、以及各编辑入口是否出现。

> **成员密钥登录与本机免登录都会把会话绑定到一位成员**（`uid` 就是他），所以「管理」与
> 「我的」两处都能用：服务器管理员能像普通成员一样在 `/user` 改自己的头像 / 名字 /
> 推流 ID，轮换自己的密钥与令牌。服务器管理员**不能被停用 / 降级 / 删除**。

### `/admin`：服务器管理（独立路由）

顶栏右上角的**「管理」按钮**（地址固定 `/admin`，**仅服务器管理员可见**）把与赛事无关的统一管理收在一处：

* **服务器状态**：站点名称 / 成员数 / 赛事管理员数 / 届次总数 / 封禁数；
* **站点**：**站点名称**（全局）——顶栏左侧、浏览器标签与主页标题都用它，留空回落「NTE 比赛」；
* **成员管理**：新增 / 编辑 / 删除成员，改权限、推流 ID、头像等；带**搜索**（名字 / uid /
  游戏 UUID / 推流 ID）与**筛选**（全部 / 成员 / 赛事管理员 / 服务器管理员 / 直播中 / 封禁中）；
  保存成员或轮换凭据后，新密钥 / 令牌以「仅此一次」弹窗展示，可一键复制；
  **成员超过 4 行自动分页**（一页 = 4 行 × 当前列数——列数是量出来的，所以手机上自然就是
  一列 4 个、宽屏上则是一整屏 4 行）；换搜索词 / 筛选条件时回到第 1 页；
* **届次管理**：全部届次（含进行中与未来）的**添加 / 关闭 / 隐藏 / 重命名 / 删除**——
  比「全部赛事」页多了**隐藏**（对访客不出现在列表里，服务器管理员仍可见）与**举办者名字**
  （鼠标悬停可看到归属 uid，便于排查）；
* **自定义 HTML**：为服务器接入统计 / 数据采集脚本，内容原样注入页面（会执行其中的 `<script>`），
  内容变化时才重新注入；
* **备份**：全站数据打包 / 下载 / 上传还原 / 周期性自动备份（详见下文「数据备份」）；
* **直播配置**：媒体服务器的根地址（WebRTC / HLS）、控制 API 地址与账号、默认流名、
  推流令牌、封面与备注。**这一整块只在这里出现**——赛事管理页一个直播字段都没有
  （直播没有总开关，见下文「直播」）；
  API 密码是凭据：只存服务端，表单只显示「已配置（留空 = 不修改）」（详见下文「直播」）；
* **界面配置**：主题色 / 自定义主题色 / 分享图 / 两个展示开关。**也只有服务器管理员能改**
  （赛事管理页不再提供这块表单，写接口同样按内容把关）；它**按届保存**，所以面板里会
  写明当前改的是哪一届；
* **成员凭据**：成员密钥与 Bearer 令牌（**只存加盐哈希**，轮换后旧值立即失效）。

### `/user`：我的资料（独立路由）

顶栏右上角的**「头像 + 用户名」**（地址固定 `/user`，任何登录用户可见）——
**服务器管理员也有这一页**（他的会话绑在自己的成员记录上，见上文）：

* 修改**名字 / 游戏 UUID / 推流 ID / QQ / 头像 / 备注**（`uid` 与权限不可改）；
* 修改**直播间名字**——开播后它就是频道里显示的标题；
* **凭据管理**：查看密钥 / 令牌是否已配置（**不可查看明文**），并一键**轮换**自己的密钥或令牌；
* **账户**：显示当前身份与网站用户 UUID，并提供**退出登录**；
* 顶部会显示**封禁横幅**（理由 + 解禁时间 / 永久 + 范围），封禁期间无法推流。

### 直播封禁与强制掐断

只有**服务器管理员**拥有全局封禁权与**解除封禁**的权利；**赛事管理员**可对自己那届
（当前届、且自己创建）**在赛直播间**签发赛事级封禁：

| 范围 | 签发者 | 生效范围 |
| --- | --- | --- |
| `global` 全局封禁 | 服务器管理员 | 任何届次都生效 |
| `event` 赛事封禁 | 赛事管理员（或服务器管理员指定届） | 仅该届生效 |

* **掐断**：`POST /api/live/bans` 会查 MediaMTX 的 WebRTC 会话，踢掉该路径的**推流端**
  （`state=publish`）会话；查不到（未配置 API / 未在推流）时封禁仍照常生效——下次拿旧令牌
  再来推流一样会被鉴权拒绝；
* **封禁时长**三选一：**永久**、**封 N 分钟**（到期自动失效），或**只掐断不封禁**；
* **展示理由**：被禁成员的**直播间卡片**与**成员信息**都会显示「封禁至 <时间> / 永久封禁」
  与填写的理由；若该成员此刻还在参加比赛，直播间卡上还会带「比赛中 · <对局>」；
* **封的是「人」，不是那串名字**：封禁记录里带 `memberUid`，而 `authorize_publish` 的
  **第一步**就是查封禁（在验令牌之前）——所以他**换令牌、改推流码都绕不过**，
  再来推流一样回「该直播间已被封禁（原因）」（有测试钉着，见 `test_live_auth.py`）；
* 配套的一条：**成员不能把推流码改成站点里已登记的流名**（主直播间默认流名 / 频道 /
  选手固定流名）。那些名字在鉴权里走白名单分支，而反查成员是按流名做的——让成员占用它，
  等于用别人的门牌号把别人的直播间顶掉。`ensure_stream_unique` 会直接拒绝（`比赛改推流码`
  也走这条规则）；
* **解除**：`DELETE /api/live/bans/{id}`——**仅服务器管理员**；解除后立即可再次推流。

### 自定义 HTML（数据采集）

服务器管理员在 `/admin → 自定义 HTML` 里填任意 HTML，会注入到页面末尾的隐藏容器
（`#customHtmlHost`）。注入时会把其中的 `<script>` 节点重新创建，因此**内联脚本会被执行**
（用于接入统计 / 数据采集）。内容只在变化时重建一次，不会因状态推送反复执行。
因为会执行脚本，**只在受信任时填写**；留空即关闭。

### 登录失败限制（类 fail2ban）

`POST /api/auth` 是唯一的暴力破解入口，因此挂了登录失败限制，参数由服务器管理员在
`/admin → 登录限制` 里配置：

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| 启用 | 开 | 关掉即完全不限制 |
| 失败次数阈值 | 5 | 统计时间窗内失败达到该次数即封禁 |
| 统计时间窗 | 300 秒 | 只统计窗内的失败 |
| 封禁时长 | 900 秒 | 期间登录回 **429** 并带 `Retry-After`；`0` = 只计数不封禁 |
| 可信反向代理 IP / CIDR | 空 | 见下 |
| 永不封禁的 IP / CIDR | 空 | 白名单，例如管理员的固定出口 IP |

**真实 IP（反向代理）**：默认只认**直连地址**（`request.client.host`），
**未列入可信代理时一律忽略 `X-Forwarded-For` / `X-Real-IP`**——否则任何人都能伪造 IP
来绕过封禁，或把别人「陷害」进黑名单。站点前面有反向代理 / CDN（如 EdgeOne）时，
把**代理的 IP / CIDR** 填进「可信反向代理」，服务端才会从转发链里取最右侧的非可信跳作为真实 IP。
管理端会显示**本次请求解析到的客户端 IP**，可据此验证代理配置是否正确；
未配置可信代理时会给出明确告警（否则所有请求同源，一处失败会误伤所有人）。

计数与封禁只在内存里（进程重启即清空）。

### 封禁 IP 列表（`/admin → 登录限制` 下半部分）

自动封禁之外，管理员还可以**手工封禁**任意 IP，并对整张表做日常管理：

| 能力 | 说明 |
| --- | --- |
| 列表 | 每条显示：IP、剩余时长（或**永久**）、来源（自动 / 人工）、原因、该 IP 的失败计数、到期时间 |
| 分页 | 服务端分页（每页 20，最多 200）：被攻击时这张表可能有成百上千条，全量丢给前端再筛最慢 |
| 搜索 | 匹配 IP 片段**或原因文字**（例如搜「爬接口」能找到同一次批量封的） |
| 过滤 | 全部 / 永久 / 临时 / 自动封禁（登录失败过多）/ 人工封禁 |
| 改时长 | 每条都能改：填秒数，**填 0 = 永久** |
| 解除 | 逐条解除，或一键「解除全部」 |

两条判定上的取舍（都写在 `login_guard` 的注释里）：

* **人工封禁优先于白名单**：白名单挡的是自动封禁（别把自己人误伤），但管理员点了
  封禁就必须生效——拦不住的话，界面写着「已封禁」而实际放行，比没有这个功能更糟；
* 只接受**单个 IP**（不是网段）：这条路径在每个登录请求上跑，必须是 O(1) 的字典查；
  网段是「可信代理 / 白名单」那种低频判断，那里才用 CIDR。

### 本机访问不设防

**本机直连（localhost / 127.0.0.1）默认不设防**：免登录、也不用担心触发登录失败限制。

* 打开页面时前端会自动向 `POST /api/auth/local` 要一个服务器管理员会话，因此在本机开发 / 运维时
  完全不用输入密钥；
* 判定相当严格，三条**同时**满足才算本机（配置项「本机不设防」可整体关闭）：
  1. 直连方是回环地址（`127.0.0.1` / `::1`）；
  2. 请求里**没有任何转发头**（`X-Forwarded-For` / `X-Real-IP` / `Forwarded`…）；
  3. `Host` 头是本机名（`localhost` / `127.0.0.1` / `[::1]`）。

  这样即使反向代理就架在本机，只要它是转发进来的（带转发头）或访问的是公网域名（Host 是域名），
  就不会被当成「本机」而拿到管理员权限；本机请求也不计入登录失败次数，避免把自己封掉。

### 操作日志（`/admin → 最近操作`）

**只有服务器管理员**看得到。服务端中间件把每个**写请求**记一条：

```
时间            谁            做了什么              结果
10-04 12:05    服务器管理员    保存配置              ✓    PUT  /api/config
10-04 12:07    未登录          重载数据              401  POST /api/reload
```

两条刻意的取舍：

* **只记「谁 / 何时 / 方法 + 路径 / 状态码」，不记请求体**——请求体里会出现
  成员密钥、Bearer 令牌、推流令牌，抄进库等于多存一份敏感信息；
* **跳过登录与媒体服务器回调**（`/api/auth`、`/api/live/auth`）：前者带密钥，
  后者是 MediaMTX 每个推流会话都会打过来的，记下来只会把日志冲干净。

失败（401 / 4xx / 5xx）会标红——「谁在乱动」最该看到的就是它。只保留最近
600 条，库里不会无限长。写日志失败**只记 warning，绝不影响请求**：它是观测手段，
不是业务逻辑。

### 数据备份（`/admin → 备份`）

**只有服务器管理员**能碰备份。一份备份就是一个 zip，打包的是**全部数据**：

| 内容 | 说明 |
| --- | --- |
| `config/nte.sqlite3` | 数据库快照：所有届次与赛程、成员与**加盐凭据哈希**、直播封禁、频道、自定义 HTML、登录限制…… |
| `data/uploads/**` | 上传的图片：通知 / 赛事信息里的插图、本地上传的头像（**同一张图只存一份**） |
| `data/avatars/**` | 旧布局的本地头像（只有老备份里才有；还原时并进统一目录） |
| `manifest.json` | 格式版本 / 时间 / 原因 / 清单（还原前会校验它） |

> 快照走 **SQLite 官方 backup API**，不是直接拷文件——WAL 模式下复制 `.sqlite3` 会丢掉
> 最近提交的事务。QQ 头像缓存（`data/avatar_cache`）**不进备份**：它可再生，装进去只是白占体积。
> 备份文件默认放在项目根的 `backups/`（已在 `.gitignore` 里，**含密钥，不要入库 / 外泄**）。

* **手动备份**：「立即备份」随时打一份；
* **周期性自动备份**：可设开关 / 间隔（1~720 小时）/ **最多保留份数**；后台巡检每 5 分钟看一次是否到点，
  到点就打一份并按保留份数**从旧到新自动清理**。服务停了一段时间后重启会**立刻补上**欠下的那一份；
* **下载**：列表里每一份都能直接下载——前端带 `X-NTE-Token` 取回二进制再本地另存
  （`core.downloadFile`），**链接里不出现会话令牌**（见「安全清单」那一条）；
* **上传并还原**：上传一份 zip 即**还原**（请求体就是原始 zip 字节，不需要额外的表单依赖）。
  还原前会校验格式、防路径穿越、确认里面有本站的库（必须有 `events` 表）；
* **还原**：列表里也能直接还原某一份。还原是**破坏性**操作，因此：
  1. 先自动打一份「还原前」的安全备份（`pre-restore`），万一还原错了还能倒回来；
  2. 覆盖数据库与图片仓库（备份里一点图片都没有时保持不动），并做一次幂等的结构升级；
     备份里若有旧布局的 `data/avatars/` 会**并进统一目录**——同一张图不会因为还原又变成两份；
  3. **全量重载内存状态**（`store.reload_all()`，连「当前届」一起换）并**注销全部会话**——成员凭据可能已经变了；
  4. 前端收到 `reauth=true` 后清掉本地会话并重新加载（本机访问会自动免登录回来）。

> 备份设置存在 `backups/settings.json`，**不入库**：这样还原一份旧备份不会把现在的备份策略一起倒回去。

> **还原不影响凭据**：盐与摘要在数据库里，跟着备份一起走，所以还原之后原本的
> 成员密钥、Bearer 令牌都照旧可用（上传前的会话仍会被注销，重新登录即可）。

### 旧数据备份（`/admin → 旧数据备份`）

与上面的「备份」是两回事，一句话说清区别：**备份是「能还原回去的现在」，这里是
「新版本已经读不动的过去」**。

计分口径从「一个 `metric` 字段」改成「类型 / 标签 / 判断标准」三件套时，
第一次启动会**自动**把老数据落成新字段。**转换之前**，服务端先把整个数据库原样
打一份快照放进 `backups/legacy/`（文件名 `nte-legacy-<时间>-<原因>.zip`），
然后才开始转换——万一转换哪里不对，原始数据还在。

* **自动**：只在真的检测到旧结构时留一份，之后不再重复（下次再出现旧结构，
  说明是还原了一份更老的备份，那时也会再留一份——这是对的）；
* **只读留存**：面板上只有「下载」和「删除」，**没有还原入口**。把它塞回新版本
  只会得到一份读不动的数据，反而更危险；
* **看内容就下载**：解压后的 `config/nte.sqlite3` 就是一份完整旧库，用任何 SQLite
  工具都能打开（面板上还会写明里面有几届 / 几位选手 / 几场比赛）；
* **与正式备份分开存放**：不会被「自动清理旧备份」顺手删掉。

> 留不下来就**不转换**：快照失败时本次升级直接跳过（数据仍按旧口径无损读取），
> 宁可不转换，也不在没有退路的情况下改库。

### QQ 机器人推送（AstrBot）

把比赛信息推到 QQ 群，走的是 **AstrBot 的 OpenAPI**（v4.18+）。

**配置**（`/admin → QQ 机器人`，仅服务器管理员）：

| 项 | 说明 |
| --- | --- |
| 启用群推送 | 总开关（关着时推送接口直接报「未启用」） |
| AstrBot 地址 | **出厂留空**，填自己那台 AstrBot 的面板地址（不带尾部斜杠） |
| API Key | 在 AstrBot 的「设置 → OpenAPI」里创建，形如 `abk_xxx`；**只存服务端**，接口不回显、不进导出。勾权限时**要带上 `file`**：发图要先上传换 `attachment_id`，缺这个权限会回 403（提示里会写清） |
| 目标群 | 填**群号**（如 `123456789`）或完整 UMO（`aiocqhttp:GroupMessage:123456789`） |
| 平台适配器 | 只填群号时用它拼 UMO（QQ / OneBot v11 / NapCat 用 `aiocqhttp`） |
| @ 的方式 | `cq`（默认）/ `text` / `none`，见下方说明 |
| 单条上限 | 超出自动**分段发送**（列表还会按页切）；下限 200 字 |
| 最小间隔 / 每小时上限 / 单次分段上限 | 频率限制，见下一节 |

配好后点「**发送测试消息**」：一分钟内就能确认地址 / Key / 目标群 / @ 方式是否都对。
旁边还有「**测试发图**」：往群里发一张当前届的比赛卡片，并把图片段**实际生效的那条路**
（字段名，或「先上传再引用」）回报给你——AstrBot 各版本对图片段的规范不一样（见下），
图片通道通不通一眼就能确认，不用等真推送。

**「图片推送」开关**（默认开）：关掉就只发文字（信息一条不少，文字里本来就带规则摘要）。
适合「群里不想要图」或者机器人对图片支持不好的场合；图发不出去时**自动退回文字**，
与这个开关无关。

**推送内容**（在「赛事管理 → 推送到群」里选，先「预览」再「发送」，发的是**当前这一届**）：

| 类型 | 内容 |
| --- | --- |
| 比赛信息 | **发一张卡片图**：名字 / 赛制 / 时间（年月日 + 星期几 + 几点开始与结束，**没填结束时间就不写**）/ 参赛人数 / 分组名单 / 简介 / 是否启用排名 + **完整的比赛规则**（随赛制自动生成）；图后面只跟一行说明 |
| 当前直播 | 主直播间是否开播 + **正在推流的选手 / 成员机位**及观看地址（WebRTC / HLS）；**全局信息、不挑届次**，预览 / 推送时会**真探一次**媒体服务器 |
| 赛程进度 | 已赛 X / Y（百分比）、进行中几场、**正在打的是谁 vs 谁**；没有在打的就报下一场；顺带报榜首 / 冠军 |
| 召集参赛 | **@ 参与名单里所有能对上的 QQ** + 比赛名称 + 时间，请他们到场准备 |
| 比赛结果 | 冠军 / 积分榜（或最终排名）+ 逐场比分（超 12 场只列最近 12 场） |
| 单届详情 | 上面「信息 + 进度 + 结果」的摘要；选定场次则细说那一场（双方、比分、胜方、状态、时间） |
| 全部比赛列表 | 所有届次（状态 / 排名模式 / 人数 / 已赛场次 / 榜首），**过长自动分段，并支持翻页** |

权限：**服务器管理员**推任意届；**赛事管理员**只能推**自己创建**的届（与赛事管理同一套归属校验）。

#### 图片推送：比赛卡片（`app/card.py`）

加了「比赛规则」之后，比赛信息在群里就是一屏接一屏的纯文本（还得切成好几段发）。
所以**比赛信息改发一张卡片图**：上面是信息栏（赛制 / 人数 / 分组 / 同场规模 / 计分口径 / 晋级名额）
与**完整的比赛规则**，一眼看得完、能直接转发，也不再受「单条消息长度」限制。

组 vs 组、组 vs 组 vs 组、四队同场都按**当前赛制**说对应的那句（规则本身由
`logic.rulebook` 按参数现算，见「比赛规则」一节），换了赛制卡片就跟着变。

**三条硬约束**（都直接关系到「别把服务搞卡」）：

| 约束 | 做法 |
| --- | --- |
| **同一份内容只画一次** | 卡片内容的 sha256 就是文件名（`data/cards/<hash>.png`）：没改过赛制 / 赛程，反复推送都直接吃缓存 |
| **不占事件循环** | 渲染在线程里跑（`asyncio.to_thread`），并发渲染有信号量限流、有超时；同一份内容并发只渲染一次（单飞锁） |
| **Pillow 是正式依赖** | 它就在 `pyproject.toml` 的 `dependencies` 里，`uv sync` / 镜像装好就**有图**。万一某个环境漏装了，才**自动退回纯文本**（信息一条不少，文本里同样带规则摘要）——那是兜底，不是「要额外装才有图」 |
| **含中文的行必须用 CJK 字体** | 西文字体（`mono` / `latin`）没有中文字形，画出来是一排空心方块（副标题那条踩过：`e902 · 筹备中 · 第 1 届` 走了等宽西文字体）。字体**也算进内容指纹**：换了字体（或这台机器从「没装」变成「装了」）指纹就变，旧图自动重画 |

* **地址只认本站签发过的**：图发在 `/api/cards/<hash>.png`（公开，因为要发到群里给 QQ 客户端拉），
  文件名是内容哈希，而且 `card.resolve()` **只认推送 / 预览时签发过的哈希**——
  没流出去的卡片就算凑出地址也读不到，不是「换个链接就能下载点什么」的口子；
* **管理端能先看图**（「赛事管理 → 推送到群 → 预览」）会直接把卡片显示出来，
  并标出「1 张卡片图 + N 段文字」；发送后的提示也会写明「图片 + N 段」；
* **图发不出去就退回完整文本**：这台机器上没装 Pillow（异常情况）、AstrBot 拒绝图片段、拉不到图——
  这三种情况都不会让群里少东西，推送里也会记一行日志说明「卡片推送失败，退回纯文本」；
* **图片段的两条路**（`send_image`，AstrBot 改过一次规范）：
  1. *老形态*——图片段里直接带地址（`file` / `url` / `image` 依次试），早期版本与部分适配器吃这一套；
  2. *新形态*——新版 AstrBot 的图片段**只认 `attachment_id`**，老写法会被回
     `400 image part missing attachment_id`；这时**自动改成两步**：先把图 `POST /api/v1/file`
     传上去换 `attachment_id`，再发引用它的消息段（引用字段从响应里**任意层级**找，
     文档没规定它在哪一层）。所以那条路要 API Key 有 `file` 权限；
  哪条路成功就**记在进程里**，之后直接用那条，不再每次白撞几个 400；
  「测试发图」会把生效的那条路（字段名 / `attachment_id`）显示出来，排障一眼可见；
* 卡片目录会按 mtime 只留最近 240 张（内容定址的目录只增不减，得有人扫一下）；
* **哪些类型不发图**：进度 / 结果 / 名单 / 列表这类**逐场次**的内容还是文本更合适（画成图反而看不快），
  所以只有「比赛信息」与「单届详情」（不带场次）会生成卡片。

#### 输出一律是纯文本（QQ 不认 Markdown）

**所有出站消息在发送前都会过一道纯文本化**：`**加粗**` → `加粗`、`## 标题` → `标题`、
`[文字](链接)` → `文字（链接）`、表格行改成 ` · ` 分隔、代码围栏去掉、列表符号统一成 `· `，
连续空行压成一个。消息构建器照常写最自然的文案，格式问题只在这一个地方兜住
（`qqbot.to_plain_text`，幂等，可重复调用）。

> 唯一不走文本的是**卡片图**（上一节）：它就是为「规则太长、纯文本撑不住」而存在的，
> 所以图里可以写细；图后面配的那几行仍然过纯文本化。

> aiocqhttp 适配器发送文本时会 `strip()` 掉首尾空白——所以出站内容不留首尾空行，
> 多行消息靠**内部换行**保持分段，不会被压成一行。

#### 群命令（配套插件）

站点自带只读查询 API，配套的 AstrBot 插件在 **`integrations/astrbot_plugin_nte_match/`**：
把它复制到 AstrBot 的 `data/plugins/` 下，填上**站点地址**与**查询 API 令牌**即可。

* **群命令**（22 条，**不经过任何大模型**）：`比赛`、`比赛直播`、`比赛列表 [页码]`、
  `比赛届次 [我的] [页码]`、`比赛信息 [届次]`（**发一张卡片图**）、`比赛进度 [届次]`、
  `比赛下一场 [届次]`、`比赛结果 [届次]`、`比赛冠军 [届次]`、`比赛名单 [届次]`、
  `比赛详情 [届次] [场次]`、`比赛UID [@某人]`（游戏 UUID，**群里直接回**）、`比赛召集 [届次]`、
  `比赛我的`、`比赛直播注册 [流名]`、`比赛资料 [字段 新值]`、`比赛重置密钥`、`比赛重置令牌`、
  `比赛改推流码 <流名>`、`比赛授权 @某人`、`比赛添加 @某人`、`比赛帮助`；
  每条都带一批别名，且**刻意收得比较宽**（`进度`、`成绩`、`下一场`、`谁赢了`、`谁在播`、
  `打到哪了`、`赢了吗`…），命令名统一带 `比赛` / `赛事` / `nte` 前缀，
  避免和 AstrBot 的内置命令（如 `/help`）撞车；
* **不依赖大模型**：命令是 AstrBot 的**命令过滤**（纯字符串匹配），在「要不要请求大模型」
  之前就处理完了；插件**不注册任何 LLM 工具、也不发 LLM 请求**（只对站点发只读 HTTP），
  所以答案稳定可复现，关掉 / 不配 provider 也照常工作。代价是「命令覆盖不到的自由问法
  没有兜底」（机器人沉默）——别名才有必要放宽，另外**问帮助还能直接回一张帮助图**。
  `比赛直播`、`比赛列表`、`比赛届次` 是全局信息（**不接届次**），前者会**真的探一次**
  媒体服务器（最多等 3 秒，单飞锁防惊群）；页面请求仍只读缓存，永远不会为直播探测而卡首屏；
* **必须先 @ 机器人或带唤醒前缀**：AstrBot 的命令过滤要求 `event.is_at_or_wake_command`
  （源码 `CommandFilter.filter` 的第一行），所以只有「@机器人 比赛进度」或唤醒前缀写法
  （如 `/比赛进度`）才会命中命令。**群里裸打字不触发**：既不 @ 也不带前缀时，机器人会
  **完全沉默**（不是坏了，是没被叫到——插件没有大模型兜底）。
  好消息是匹配按**词边界**（`指令名 + 空格` 或完全相等），所以短命令不会吞掉长命令：
  「赛事信息」不会被「赛事」抢走；
* **插件启动会自检**：加载时调一次 `/api/bot/ping`，把「连上了哪台站点、当前是哪一届、
  共几届」写进日志；地址或令牌配错会**立刻** warning，不用等群友发命令才发现；
* **命令参数一律宽松解析**：`比赛列表 第2页` / `2` / `2 页` 都认。
  （参数**刻意声明成字符串**：AstrBot 在参数带 int 默认值时会对实参做 `int()` 强转，
  转不动会直接抛异常、整条命令失效——这是框架行为，只能在参数类型上规避）；
* **届次要写明**：可以写 `e001` / `1` / `第2届` / 名称片段；**不写会提示你补上**，不会去猜——
  站点内部那个「当前届」指针（谁最近打开过就是谁）只是实现细节，不能当用户可见的默认值；
  匹配到多届会列出候选，找不到会**列出可用编号**，用户自己就能改对；
* **`比赛届次` 会自动分页、并且「多了就私聊」**：每页 10 条，一页装不下时
  **私聊发给喊命令的人**（群里只留一句「已私聊发你第 1 页」+ 下一页怎么写），
  免得一串届次把群刷了；写「我的」只看**自己创建的**届（站点侧按 QQ 过滤，与
  「谁能召集」同一套归属），也照常分页；私聊发不出去（没加好友 / 没配推送）就退回群里发当前页；
* **帮助图**（`/help.jpg`）：站点在 **`/help.jpg`** 提供它（路径短、不随资源版本号变，
  换图**地址不用改**），**插件侧不用配任何东西**：`比赛帮助` 会先探一下这张图在不在——
  在就当场发图，没放图则回私聊文字说明（不会发破图）。想用别处的图，就在插件配置里
  填 `help_image` 覆盖默认值。
  **图不是放进去的图，是代码渲染出来的**（文字由代码排版，一个字都不会错；命令是精确匹配的，
  写错一个字群友照着打就没反应），而且 **`static/help.jpg` 不入库**：

  * **服务启动时自动重画一份**（`app/helpcard.py`，跑在线程里、不拖慢启动）；
    文案改了重启一次就是新图，不存在「仓库里那张图比文案旧」这种事；
  * 文案在 `app/helpcard_content.py`（**零依赖**，测试直接读它比对插件的 `HELP_TEXT`），
    排版在 `app/helpcard.py`（配色照站点 CSS，所以是一套观感）；
  * 这台机器上万一没装 Pillow 就只记一行日志：图和文字说明二选一，功能一点不少；
  * 想立刻看一眼新版式、或把图写到别处：

  ```bash
  uv run python tools/make_help_card.py   # → static/help.jpg
  ```

  * 出图时会顺手写一个 `static/help.jpg.src.sha256`（源文件指纹，同样不入库）：
    **本地若有一份图**，`tools/check_assets.py` 与测试据此拦住「手改过的图与文案对不上」
    ——那等于发一张写着旧命令的图，群友照着打毫无反应；
  * 玩法与清单见 `integrations/astrbot_plugin_nte_match/HELP.md`；
* **令牌**：在「服务器 → QQ 机器人 → 查询接口令牌」生成（形如 `nte_…`），
  **只存加盐哈希、明文只显示一次**，重置后旧令牌立即失效；清除即关闭查询 API。

**成员不用登录站点也能自助搞定自己的资料**（按 QQ 认人、**只能动自己的**；@ 某人 = 服务器管理员代办，
**结果一律只发被操作的那个人**）：

| 群里发 | 做什么 | 结果去哪 |
| --- | --- | --- |
| `比赛直播注册 [流名]` | **开播要用的东西一次给全**（见下表） | **私聊**给**被操作的那个人** |
| `比赛资料` | 完整资料 + **每一项怎么改**（用户不用记命令：答案里就写着命令） | **私聊**给**被操作的那个人** |
| `比赛资料 名字 新名字` | 改一项（名字 / 游戏UID / B站 / 推流码 / 直播间 / QQ；写「清空」清掉） | 同上（并回一份新资料） |
| `比赛UID [@某人]` | 查游戏 UUID（自己或 @ 到的人） | **群里直接回**（它不是凭据，举办者天天在问） |
| `比赛重置密钥 [@某人]` | 换一把登录密钥（旧密钥立即失效） | **私聊**给**被改的那个人** |
| `比赛重置令牌 [@某人]` | 换一把直播令牌（Bearer；**要求先有推流码**） | **私聊**给**被改的那个人**（含推流地址） |
| `比赛改推流码 <流名> [@某人]` | 改推流码（推流 ID；令牌不变）——等同 `比赛资料 推流码 <流名>` | **私聊**给**被改的那个人**（含新地址） |

`比赛直播注册` 的三种情况（这条命令是**唯一**能自助搞定推流的入口，所以每种都说清楚）：

| 他现在的状态 | 给什么 |
| --- | --- |
| **还没有推流码**（第一次注册，最常见） | 给一个推流码 + 一把新令牌 + 推流地址 + OBS 注意事项 |
| 有推流码、没令牌（老数据里令牌是空的） | 推流码照用，补一把新令牌 |
| 两个都有 | **什么都不改**，只把推流码 / 推流地址 / 直播间地址与注意事项给他，并提醒「令牌是原来那一串；忘了就发『比赛重置令牌』换一把新的」 |

> 「有推流码的人，令牌绝不会被顺手换掉」是刻意的：令牌只存哈希、取不回明文，而重置是**破坏性**动作
> ——正在推流的人会被当场顶下线。至于「还没有推流码」的人：新建成员时站点会随手生成一把令牌，
> 但**从来没发给过他**（建号那条私聊里只有登录密钥），所以他手上其实一把都没有；
> 而没有推流码的人**不可能正在推流**（`live.authorize_publish` 是按流名反查成员后校验令牌的），
> 换掉那把没人见过的令牌不影响任何人——这才让「注册」这条命令能一次给全。

* **不 @ 人 = 改自己**（谁都能改自己的）；**@ 了人 = 替 TA 改**，这需要**服务器管理员**；
* **新值只发给被改的那个人**：代改时服务器管理员也看不到——他要的只是「帮不上线的人重置」。
  私聊里会写明「这次由服务器管理员「某某」帮你重置」，本人对不上号就能立刻再改一次；
* **新值不由接口回话**：密钥 / 令牌只在**站点发出的那条私聊**里出现，响应体里只有
  「发了没发出去」——插件拿不到明文，也就**打不进群里**（这是结构上的保证，不靠自觉）；
* **私聊里必带那句提醒**：任何拿到密钥 / 令牌的人都能用它登录 / 推流，觉得可能泄露就
  **立刻再重置一次**（旧值随即作废）——这正是自助重置存在的意义；
* **令牌要有推流码才发**：没有推流码（推流 ID）的成员，令牌没地方填，先让他改推流码；
* 同理，「`比赛添加 @某人`」新建成员时，**登录密钥由站点直接私聊给本人**（含同一句提醒）。

> **`比赛召集` 是真正的 @**：插件跑在 AstrBot 内部，用消息链的 `At` 组件发 @；
> 而 HTTP 推送只能把 `[CQ:at,qq=…]` 写进文本（OpenAPI 没有 at 段）。想稳定 @ 到人就用这个命令。

> **召集有两道闸门**（它天生会 @ 一大片人，不该谁都能触发）：
> 1. **认身份**：规则只有一条——**谁创建的届，谁可以召集**（服务器管理员另有全局权限：
>    他建的届自然归他，别人建的届他也能召集）。站点提供 `GET /api/bot/managers`
>    回这批人的 QQ，插件拿它比对发命令的人——因为**在群里只能靠 QQ 认人**，
>    而谁是创建者只有站点知道。所以一位赛事管理员能召集的是**他自己创建的那些届**，
>    不是随便是哪一届；**写错届次**是最常见的失败原因，这时插件会把「你自己创建的届 +
>    该敲的命令」一起回给他（接口的 `mine` 字段）。
>    代价：创建者得在「我的」页**填上自己的 QQ**，否则名单为空、谁也召集不了
>    （提示会点名说是谁还没填）；
> 2. **冷却**：同一会话默认 **60 秒最小间隔 + 每小时 6 次**，插件配置里可改
>    （`call_cooldown` / `call_per_hour`，都设 0 = 关掉）。

#### 群里授权 / 添加成员、私聊投递

除了查询，插件还能做三件**写**的事——闸门全在站点这一侧，插件只是转达：

| 命令 | 做什么 | 谁能用 |
| --- | --- | --- |
| `比赛授权 @某人` | 设为**赛事管理员**；还不是成员就自动建号 | 仅服务器管理员 |
| `比赛添加 @某人` | 添加为**普通成员** | 仅服务器管理员 |
| `比赛我的` | 私聊发本人的**推流地址 + 站内直播间地址** | 任何登记了 QQ 的成员 |

设计上刻意这么定：

* **认人只认 QQ，且由站点判定**（`POST /api/bot/members` 收 `actorQq`，站点按它查成员、
  判权限）。插件那边的提示只是体验层——绕过插件直接调接口也过不了这一关，因为
  **令牌只代表「这是本站的机器人」，不代表权限**；
* **不允许经这条路授予 `server_admin`**：全站只有一位服务器管理员、最高权限，请到
  「服务器 → 成员管理」改；
* **已经是成员就只改权限**，不碰他的密钥与令牌（换权限不该顺手把人家的登录口令作废）；
* **新成员的登录密钥只私聊给本人**，且只出现一次；发不出去就只回一句「让 TA 自己重置换新」，
  **绝不发在群里**——而且这条私聊**由站点直接发**：`POST /api/bot/members` 的响应里
  只有 `keySent` 布尔，**没有明文**，插件连「打错到群里」的机会都没有；
* **本人可自助换凭据**（`POST /api/bot/credential`）：换登录密钥 / 换直播令牌 / 改推流码。
  同样按 `qq` 认人（只能动自己的），新值同样只走私聊、响应里只有 `sent`；
* 为什么私聊由**站点**代发：站点本来就握着 AstrBot 的 API Key 与统一发送通道（群推送走的
  就是它），插件不必再依赖某个 AstrBot 版本的私聊接口；凭据只走这条路，也就有了
  「明文不经过插件」这条结构性保证。

#### 赛前提醒（站点侧定时任务）

开赛**前一天**与**前 2 小时**，站点自动在群里 @ **举办者**（`app/remind.py`，
针对**当前届**——群里就一个推送目标，提醒自然只盯当前这一届）。
放在站点而不是插件里：只有站点知道开赛时间，也只有它握着推送通道。

* 开关与提前量在「服务器 → QQ 机器人 → 赛前提醒」（默认开，提前量 `1440,120` 分钟）；
* **只在【提前量 − 1 小时, 提前量】窗口内发**：服务器中途重启时，不会把「明天开赛」
  补发成「还有 3 小时开赛」——宁可少发一条，也不发一条错的；
* **同一条提前量只发一次**（标记写在 `meta` 表，进程重启也记得）；发送失败**不记标记**，
  下一轮还会重试；
* 举办者没登记 QQ 时退化成 `@名字`（纯文本）；连归属都没记的届（老库 / 出厂那一届）
  @ 服务器管理员。
>
> 注意站点那套推送限流**管不到插件**：它只作用于网页「推送到群」的 HTTP 路径，
> 而插件是直接往群里发的，所以冷却必须在插件侧单独做。

#### 频率限制（防止把机器人刷到风控）

推送接口自带限流，参数在 `/admin → QQ 机器人` 里可调：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| 两次推送的最小间隔 | 20 秒 | 防手滑连点；`0` = 不限制间隔 |
| 每小时最多推送 | 30 次 | 按自然小时计，防长时间高频刷群 |
| 单次最多分段 | 8 段 | 超出直接**拒绝**并提示改用分页；分段之间另各停 0.5 秒 |

* 一次推送**无论切成几段都只算 1 次**；
* **预览不占额度**（它不碰机器人）；「发送到群」与「发送测试消息」**都占**（它们真的发了消息）；
* 发送失败也占额度——请求确实打到机器人了；
* 触发限流回 **429** 并带 `Retry-After`，前端把原因直接显示出来（「推送太频繁：请等 N 秒」）；
* 额度是**内存态**，进程重启即清零——限流管的是「当下」，不需要持久化；
* 面板实时显示「限流中：还需等 N 秒 / 本小时已推 X／Y 次」，预览一次不消耗额度。

#### 把机器人拉进群

**是的，机器人必须在群里**，否则它没法往这个群发消息：

1. 在 QQ 上把 AstrBot 那个机器人账号**拉进目标群**（部分平台还要给它发言权限、确认没被禁言）；
2. 拿到这个群的**群号**——从 AstrBot 的日志 / 会话记录里看（OpenAPI **没有**
   「列出所有群」的接口，只能自己取一次然后存下来）；
3. 把群号填进「目标群」（只填数字即可，会自动拼成 `aiocqhttp:GroupMessage:<群号>`）；
4. 点「**发送测试消息**」，群里能看到就说明通了。

> **关于 @**：AstrBot 的 OpenAPI 目前的消息段只有 `plain / reply / image / record / file / video`，
> **没有 at 段**，所以「@」只能写进文本里，能否真正变成 @ 取决于适配器：
>
> * `cq`（默认）：文本里写 `[CQ:at,qq=123456]`——OneBot v11 / NapCat 系按 CQ 码解析，通常能 @ 到人；
> * `text`：退化成纯文本 `@123456`；
> * `none`：完全不 @，只列名字。
>
> 拿不准就用「发送测试消息」点一下，哪种真能 @ 一眼可见。UMO（群标识）也**没有查询接口**，
> 需要你自己从 AstrBot 的日志 / 会话记录里拿到群号填进来。
>
> **想要稳定 @ 到人，用插件的 `比赛召集` 命令**（见上文「群命令（配套插件）」）：
> 插件跑在 AstrBot 内部，能直接构造 `At` 消息组件，不受这个限制。

### 赛事归属：赛事管理员只能管自己的届

新建赛事时会记录**创建者 uid**（`EventInfo.ownerUid`）；赛事管理接口统一做归属校验：

* **服务器管理员**：放行任意届（他创建的届记为服务器所有，其他赛事管理员不能改）；
* **赛事管理员**：只能切换 / 重命名 / 改状态 / 删除**自己创建**的届，否则回 **403**；
  无主（历史数据、`ownerUid` 为空）的届一律只有服务器管理员能管；
* 「全部赛事」页只对**自己拥有**的届显示管理按钮，别人的届点进去就是只读查看；
* **举办者会显示成「头像 + 名字」**：主页与「全部赛事」的卡片上单独一行，「届次管理」里在标题右侧
  （存储层只存 uid，由列表接口配上成员的显示名与头像——uid 那串随机字符对谁都没用；
  历史无主数据或成员已被删除时显示「服务器管理员」）。赛事管理页打开别人的届时也会写明
  「这一届由 XXX 举办」并给出出路，**不会**让你去猜为什么保存失败。

### 搜索与筛选

* **选手页**：搜索框（姓名 / 编号）+ 筛选下拉——全部 / 已参与本届 / 未参与本届 /
  直播中 / 封禁中；被禁的选手卡上直接标出封禁时间与理由；
* **成员管理页**：独立搜索 + 权限 / 直播中 / 封禁中筛选；
* 两处搜索都给输入做了防抖，只重绘网格、不重建整页（不会丢焦点）。

### 成员与选手的关系（「选手就是成员」）

**每一位选手都对应一位全局成员**，两边是同一个人的两种视图：

* **自动迁移**：升级到本版本后**首次启动**会把历届所有选手**一次性转成成员**——
  继承姓名 / QQ / 头像 / 游戏 UUID / 推流 ID，**权限默认「成员」**，并写回选手的 `memberUid`
  （幂等：跑过即打标记，之后不再扫描全库；日志会记一笔「已将历届选手迁移为成员」）；
* **自动建号**：新增选手时，若没有指定「关联成员」，会按**游戏 UUID**、或「姓名 + QQ」
  自动匹配已有成员，匹配不到就新建一位（权限「成员」）；
* **双向同步**：选手侧可维护姓名 / QQ / 头像 / 游戏 UUID / 推流 ID；成员侧（`/admin` 或 `/user`）
  一改，各届里关联的选手会跟着更新（推流流名跟随成员的**推流 ID**）；
* 成员的封禁状态会显示在这位选手的卡片与其直播间上；
* 报名池仍按每届独立维护（谁在本届上场由参与名单决定），成员账号则全局共享；
* **名单的来源是成员列表**：管理端「本届参与名单 → 从成员列表选择」列出全部成员，
  勾一位就参加这一届——本届还没有档案的按成员资料自动建好（姓名 / QQ / 头像 / 游戏 UUID），
  取消勾选只把他移出名单、**档案保留**（档案一删，赛程与比分就断了）。
  接口是 `GET /api/roster/members`（候选）与 `POST /api/roster/members`（保存）。

## 排名开关（与已退休的「比赛类型」）

平台不绑定具体项目，用**排名开关**在「竞技」与「娱乐记录」之间切换。

### 「比赛类型」已退休

以前每届可以选「比赛类型」（排球 / 赛车 / 摄影…），它只干一件事——把「选手」换成
「车手」、「对局」换成「赛段」，顺带在赛制面板提示一句惯用计分口径。

**现在统一用一套固定用词**（选手 / 对局 / 比分 / 场地），不再按类型换称呼。理由：

* 组织者真正要的是**规则跟着赛制走**，称呼是另一层需要维护、且最容易和实际对不上的东西；
* 它带来的唯一「功能」（计分口径提示）本来就属于**赛制面板**——那里现在直接摆着
  计分类型 / 标签 / 判断标准三项，以及它们对实际结算的影响，不需要再转发一次。

实现上：界面上不再提供这一项，`defaults.SPORT_WORDS` 是唯一的用词来源；
老库里的 `events.sport` 字段**保留但被忽略**（不动数据：删列等于对旧库做破坏性迁移，
而它只是个字符串），`sport_meta()` 也留成了「无论传什么都回同一套词」的兼容壳。

### 比赛简介（≤30 字，可留空）

由**赛事创办者**在「赛事管理 → 赛事信息」里填写的**比赛简介**，长度上限 **30 个字**（按字符计，
输入框 `maxlength` 挡在前面，服务端再硬截一次兜底）：

* **留空**：总览与主页 / 全部赛事的卡片**都不显示**这一项，也不占位；
* 填了：出现在总览顶部一行与届次卡片里一行；推送比赛信息到群时也会带上。

### 排名开关（娱乐记录模式）

关闭「排名模式」即为**娱乐性质**，只为方便记录分数 / 场次：

* **不排名、不晋级、不产生冠军**：总览只给「参与人数 / 场次进度 / 进行中」，
  「积分榜 / 对阵图 / 冠军横幅」一律不展示；规则面板会多一段「娱乐模式（不排名）」说明；
* **不判胜负**：服务端强制允许平局，录分时**不必指定胜方**——双方同分就自动记为平局，
  绝不会因为「没点胜方」而保存失败（淘汰赛阶段同样适用）；
* 规则面板与诊断面板都会提示：娱乐模式下建议用**积分制**逐场记录（淘汰赛必须有胜者才能推进）；
  新建届时若未指定赛制，娱乐赛事会**自动落到积分制**；
* 娱乐记录不一定是 2v2：在「赛制」里把每方人数（`teamSize`）调成 1 人，两位参赛者就能开局，
  也可以直接在赛程里「追加空场次」再人工安排出场。

## 两种赛制

**积分制**与**锦标赛制**并存，**每届赛事单独选择**：新建届时选择，之后也可在管理端
「赛制」面板随时切换（切换会清空该届赛程，避免两套规则混用；报名池与队伍保留）。

前端会根据赛制切换整套界面：积分制显示**积分榜 / 选手近况 / 逐局卡片**，
锦标赛制显示**树状淘汰赛对阵图 / 小组赛积分表 / 冠军横幅**。

总览页的淘汰赛对阵图是**带连线的树状图**：胜者组 / 败者组各一条带（配色区分），
逐级向右汇入总决赛与冠军框；每个对阵框里是**双方选手头像 + 队名 + 小组战绩
（如「A 组 · 2胜1负」）+ 本场比分**，已分胜负的连线会被点亮、进行中的用虚线，
点方框即可为管理端录比分（弃权在录分弹窗里）。

打完的比赛会把成绩说全：**各轮成绩 / 双方合计 / 起止时间 / 本场时长**
（对局卡的成绩条 + 时间行，树状图的框内比分与用时）。

赛程页按**阶段 → 轮次**两级分类，数量随赛制自动变化：

```
小组赛   A 组 · 第 1 轮 / A 组 · 第 2 轮 / … / B 组 · …
胜者组   十六强 / 八强 / 半决赛 / 胜者组决赛
败者组   败者组第 1 轮 / … / 败者组决赛
总决赛   总决赛
```

同一轮里有几场就是几张卡，每张都带**对局编号**（`G-A-1-1`），
不会再出现「两张一模一样的 A 组 · 第 1 轮」。

### 计分口径：类型 / 标签 / 判断标准

「这一届的成绩长什么样、怎么比」由**三个互相独立的开关**决定（管理端「赛制」面板最上面那一组）。
拆成三件事，是因为它们本来就是三件事——「时间 + 用时 + 数值低胜」是最常见的一种组合，
而不是唯一一种。

**① 计分类型**：决定**怎么录入、怎么显示**（与谁赢无关）

| 类型 | 适合 | 录入 | 内部存储 |
| --- | --- | --- | --- |
| **自然数**（`integer`，默认） | 排球、篮球、卡牌、击杀数 | `25` | 原值 |
| **小数**（`decimal`） | 评委打分、体测测量值 | `8.75` | **千分之一**（8750） |
| **时间**（`time`） | 赛车、跑酷、速通、越野 | **时 / 分 / 秒** 三个输入框 | **毫秒** |

小数与时间都**不存浮点**：它们要参与求和与并列比较，浮点的累计误差会让「并列」不可靠。
放大成整数之后，排序、求和、判并列全是在整数上做——这也是「0.1 + 0.2 != 0.3」这类
问题永远不会出现在积分榜上的原因。

**② 计分标签**：只影响**文案**。预设「得分 / 评分 / 用时」，也可以自己填（如「击杀数」）。
选「时间」+「用时」时页面就写「用时：1:23.456」；留空则按类型给默认。

**③ 判断标准**：决定**谁赢**。`数值高胜`（分高者赢）/ `数值低胜`（成绩小者赢）。
方向只由它决定——类型只管解析与显示，「时间 + 数值高胜」是合法组合（虽然少见）。

几条贯穿全站的约定（都是刻意的）：

* **`0` 在数值型里是合法成绩，在时间型里才是「没有成绩」**。评委真的会打 0 分，
  速通不可能 0 毫秒跑完——所以「没填 / 退赛」不能只有 0 一种写法：
  数值型用 ``-1``（不可能出现的负数）作哨兵，时间型沿用 0（老数据正是这么存的）。
  没有成绩的一方在任何口径下都排最后；否则数值低胜里「0 秒」会被当成最快的人——
  这是整套抽象里唯一一个**静默且致命**的坑，后端（`app/metrics.py`）、前端（`core.js`）
  与测试三处同时钉住它；
* 「**有没有成绩**」（判定胜负、排名、完成场次）与「**有没有录入过**」（这场比赛动过没有、
  要不要锁住对阵）是两件事：数值型的 0 是合法读数，但它和旧库里从没打过的 0
  长得一模一样，所以后者不认它（`has_result` / `has_entered`）；
* 时间显示「够用就少」：整十毫秒两位（`1:23.45`），否则三位（`1:23.456`）；小数去掉末尾的 0；
* 小组赛排名在数值低胜时按「**完成场次 → 总成绩**」：先看跑完了几场，再比总成绩，
  免得「一场没跑完」的人因为成绩小而占到便宜；积分制平手时同理；
* 判定、名次、名次分、晋级与积分榜排序**全都只认「谁的名次靠前」**，
  所以三种类型共用同一套结算引擎——时间型不需要另写一套淘汰赛。

**老数据升级是无损的**：历史上只有 `metric` 一个字段（`score` / `time`），
升级时映射为「自然数 + 得分 + 数值高胜」/「时间 + 用时 + 数值低胜」——
**数值一个字节都不动**，只是把含义拆成了三个字段；排序结果与改造前**完全等价（含并列）**。
升级前会自动留一份旧库快照，见下文「旧数据备份」。

> 唯一的语义变化：数值型里旧数据存着的 `0` 现在读作「0 分」（而不再是「没填」）。
> 排序结果不变（数值高胜里 0 本来就垫底，而旧数据不可能有数值低胜），
> 但那些从没录入过的旧行会显示成 `0` 而不是「—」。新录入一律用 `-1` 区分「没填」。

### 轮次：一场可以记多轮，大比分自动算

**默认一轮**，可以随时「+ 添加一轮」（想删就点那一行右边的 ×）。判定不需要另一套结算：
录分弹窗里逐轮填成绩，`tournament.judge_round` 会把「赢的轮数」当作**大比分**、
把各轮成绩合计当作**总成绩**：

| 录入 | 结果 |
| --- | --- |
| 25:20 / 20:25 / 25:18 | 大比分 2:1，总成绩 70:63，前者胜 |
| 25:20 / 25:18 | 大比分 2:0（后面那轮不必打，照样算赢） |
| 只填本场成绩 3:1，不加轮次 | 照旧按本场成绩判定（老习惯保留） |

**大比分打平**（如 2:2）时再比总成绩（各轮合计）；连总成绩也相同就交回管理员指定胜方。

数值低胜（时间型）同样支持多轮：多轮就是「跑几次」，每轮成绩小者赢这一轮，
大比分仍是「赢的轮数」（计数，多者胜），总成绩是各轮成绩之和——所以
`1:23.45 / 1:25.10` 记的是两轮用时，而不是「时间的大小」。

弹窗里的折叠关系（从上到下就是录入顺序）：① 实时预览（大比分 / 胜负 / 各轮明细）→
② 每一方的大比分与总成绩（只读）→ ③ 轮次录入 → ④ 「直接填本场成绩」（**只在没有任何轮次时出现**，
与 ③ 互斥）→ ⑤ 胜方 / 本场时长 / 起止时间 / 备注（收在可折叠区里）。

**录入与口径对不上时会提示**（不阻断保存，只在管理端与日志里说出来）：某一轮只填了一方的
成绩（那一轮不会有胜负）、已分出胜负却有一方没有成绩（多半是漏填）。

### 赛制一：积分制（league）

```
参与选手 ──每局自动 2v2──▶ 逐局阵容（可换人 / 补位）
  └─ 每局独立结算：胜 +pointsWin、负 +pointsLose、平 +pointsDraw
      └─ 按均分（总得分 ÷ 场次）降序排名，满 minRankPlayed 场才参与名次
```

* 生成赛程时可选**动态轮换**（按参与名单自动排阵，尽量不重复搭档 / 四人组合、均衡出场）
  或**固定队伍**（按队伍配置轮转对阵）。
* **追加补赛**：为出场次数最少的选手补局，不影响已录入比分。
* 点击对局中的某位选手即可**给他安排替补**（仅这一场 / 本场及之后 / 全场），也可移出阵容、补空位。
* 参与名单变化时，未结算的对局会**自动重排**（已结算的比分不受影响）。

### 赛制二：锦标赛制（tournament）

```
参与选手 ──随机组队──▶ T 支固定队伍（每队 teamSize 人，全程不换人）
  └─ 小组赛：分 G 组轮转，每场 P 队同场（P = 2/3/4），按名次分排出 1..T 的总排名
      └─ 淘汰赛：总排名前 B 名晋级（B = 你选择的淘汰赛规模）
          ├─ 胜者组 WB：单败淘汰，B/2 → B/4 → … → 1
          ├─ 败者组 LB（可关）：胜者组落败者依次进入，共 2k-2 轮（minor / major 交替）
          └─ 总决赛 GF：胜者组冠军 vs 败者组冠军（单场定胜负）
```

#### 每个组的人数（可调，默认 2）

「随机组队」时可改每队人数（1~6 人），并可选**零头并入**——凑不满整队的人平均并入
前面的队伍，这样没人会被落下（各队人数因此可能不等，人数少的队伍会以少打多）。
组队台上还能逐队拖拽微调；`team_size` 只是「随机组队」的默认值与组队台的满员提示。

#### 组队台：队伍的一切都在卡片上改

原「队伍信息」面板已**合并进组队台**（它和组队台改的是同一批字段，两处重复的表单只会各自漂移）。
现在每支队伍就是一张卡片，卡片上直接改：

* **队名 / 缩写**：就地输入（改的是本地草案，不重绘本页，所以不会打断正在输入的内容）。
  **队名上限 6 个字、缩写上限 4 个字符**（按字符计）；队名旁边有个「**自动**」按钮，
  随机取一个 **2~4 字**的队名（如「霓虹」「深渊小队」），重复会自动避开——队名短一点
  才像队名，赛程表与对阵图里也放得下（老数据里更长的队名照常显示，限制只在编辑时生效）；
* **主题色**：卡片**左边框就是它的颜色**；点「自动」按队伍序号取色（与随机组队同一套调色板），
  也可以自己挑一个——自己挑了就不再跟着自动走；
* **成员**：拖拽编排（拖进别的队伍 / 拖回候选池；队伍满员时挤出一人回候选池）；
* **换组**：与**另一个分组**的队伍互换分组（分组只在生成赛程时用得上，换完要重新「生成赛程」）；
* **删除分组**：队员回到候选池（有队员时会先确认一次）；
* **保存队伍**：**没有成员的分组自动删除**（不必手动清空，保存后会告诉你清理了几个）；
  如果队伍被增删，服务端会清空赛程与比分 —— 那种情况保存前会确认一次。

> 空分组在接口层也会被丢弃（`PUT /api/teams` 返回 `droppedEmpty`）：空队伍在赛程里
> 就是个永远打不了的席位，不该靠调用方守规矩。

#### 每场同场队伍数（组 vs 组 / vs 组 / vs 组）

`teamsPerMatch` 取 2 / 3 / 4，**作用于小组赛**：

* 圆桌轮转法编排，每一轮内每队最多出场一次，各组内出场次数保持均衡；
* 队数不是 `per_match` 的整数倍时**均分到各场**（6 队 / 同场 4 → 3 + 3，而不是 4 + 2），
  实在排不下的队这一轮轮休；
* 分组数会自动挑一个「每组队数正好排满整场」的方案（12 队 / 同场 3 → 2 组各 6 队），
  也可以在赛制里手填组数；
* **淘汰赛恒为 2 队对阵**——这是正规赛事的通行做法，也保证「晋级 / 淘汰」定义唯一。

#### 败者组开关

| 开关 | 含义 | 结构 |
| --- | --- | --- |
| 开（默认） | **双败淘汰**：输一场进败者组，输两场才淘汰 | 胜者组 + 败者组 + 总决赛 |
| 关 | **单败淘汰**：**输一场即淘汰** | 只有胜者组，最后一轮就是决赛 |

其他规则：`T ≤ 2` 时跳过小组赛直接打决赛；胜者组首轮败者两两配对进入败者组，
之后每轮败者进入败者组的 major 轮并与败者组幸存者**反向配对**，尽量避免刚打完又相遇；
总决赛单场定胜负（不做 bracket reset）。

「败者组比赛成员」由程序按比赛进程**自动推导**：每个淘汰赛对局只声明席位来源
（如 `WB-1-2:败者`），双方由上游结果实时计算，因此不存在需要手工维护的中间状态。
重置某场比赛时，依赖它的下游对局会在同一次前向遍历中自动作废。

#### 小组赛排名：名次分

每场比赛按**名次分**结算：同场 P 队时第 1 名得 P 分、第 2 名 P-1 分……最低 1 分
（2 队即 2/1，3 队即 3/2/1，4 队即 4/3/2/1）。这样 2 队对阵与多队同场可以放在同一张表里比较。

排序：**名次分 → 净胜分 → 总成绩 → 队名**（完全确定，无随机；数值低胜时把中间两项换成
「完成场次 → 总成绩」）。小组总排名按「各组第 1 名优先、再各组第 2 名……」排列，
因此各组头名稳进淘汰赛。

#### 录入比赛结果（自动判定胜负）

一个弹窗把能填的都填了，**胜负与名次全部自动判定**：

| 填什么 | 怎么用 |
| --- | --- |
| 轮次（2 队，如 25:20 / 22:25 / 15:12） | 自动算出**大比分**（2:1）与**总成绩**（62:57） |
| 本场成绩（多队同场填各队成绩） | 直接比较，按判断标准排名次 |
| 小分 / 细则分 | 成绩相同时的第二顺位比较值 |
| 本场时长（分钟） | 记进场次信息；留空则回退到起止时间差 |
| 胜方 | 默认「自动判定」；并列第一或想人工指定时再选 |

判定顺序与后端 `tournament.judge_round` 一致：**轮次 → 本场成绩 → 小分**。
弹窗里会实时显示推导结果（如「AB 胜（A 2 : B 1）」）。
并列第一且未开启平局时会**拒绝保存并提示指定胜方**，不会产生「没有胜者」的对局卡住淘汰赛。
指定胜方后，该方名次钉在 1，其余按得分顺序依次排 2、3、4。

#### 直播：选手推自己的流名，赛程里只管要地址

**选手的推流标识就是他自己的流名**（在选手名单里设置一次，全局唯一），
因此整届赛事地址固定不变，换比赛不用重推：

```
选手 甲（流名 tom）→  https://live.shiyora.net:8889/tom/whip   ← 一直用这个推
```

* **赛程里没有直播开关**：每张对阵卡的「**直播地址**」按钮只用来**看 / 复制推流地址**
  （按套分成 WebRTC / TCP 两张表，逐项列出**本场每位选手**的地址）；
* **直播没有总开关**：只要有赛事就允许直播（那个「启用直播」开关已整体移除——
  它拦不住媒体服务器，只会让本站自己看不见直播）。媒体服务器地址、API 账号与凭据
  都在**服务器管理 → 直播配置**里，只有服务器管理员能改；
* 观众在直播页**按比赛筛选机位**（见下文「用户端看直播」）——
  「谁在推」由选手流名决定，「看的哪场」由比赛编号决定，两者不再搅在一起。

**「直播中」只标真的在推流的人**：本站会问媒体服务器的控制 API
（MediaMTX `api: yes` + `apiAddress: :9997`，在「直播配置」里填地址），
只有它上报 `ready` 的机位才算直播中；查询不到（未配置 / 不可达）时**一个都不标**，
并在「直播信息」面板里说明原因——不给观众假的直播标记。
前端每 15 秒问一次（服务端缓存 8 秒），集合变化时才重绘。

#### 快速创建分组（开赛前一键）

管理端「赛程与系统」与「组队台」都有 **快速创建分组**：比赛还没产生任何结果时，
一键完成「重新随机组队 + 生成赛程」，弹窗里可微调并可**实时预估结构**：

```
24 人 / 同场 2  →  10 支队 | 2 组[5, 5] | 8 强（八强 → 半决赛 → 胜者组决赛）| 共 30 场
```

* 参赛人数变化时结构自动适配：**人少 → 少分组、短赛程**（4 队即从「4 强」起步），
  **人多 → 拉长赛程**（16 队从「16 强」起步、32 队从「32 强」起步，实测 32 人 → 16 强 / 54 场）；
* **小组数（0 = 自动）**：自动策略是「**在每组都排得满一场的前提下，尽量多分组**」——
  人越多组越多（8 队 → 2 组、12 队 → 4 组、24 队 → 8 组，每场 2 队同场时每组至少 3 队）。
  为什么倾向多分：一组里塞太多队的代价是小组赛按平方涨、出线名额又少；分细一点，
  小组赛更短、淘汰赛更热闹。填了具体数字就完全按填的来（规则面板会写明「手动设定」）；
* 可调：每个组的人数、小组数（0 = 自动）、淘汰赛规模、每场同场队伍数、败者组开关、随机种子；
* 已产生结果时会**明确警告**并二次确认（会清空全部比分与晋级关系）；
* 预估走只读接口 `POST /api/tournament/preview`，**不写库**；确认后由
  `POST /api/tournament/generate`（带 `reform: true`）一次落库。

#### 开赛前换对手（调整小组赛对阵）

开赛前可以换对手：**点一个队徽，再点同一组、同一轮里的另一个队徽**即可对调。
每轮每队仍然只打一场，场次数与编号都不变；界面上还会给出「组合覆盖 X/Y」，
重复组合会标出来但不拦（要不要保留重复是组织者的自由）。

* 关窗口时如果还有**没保存的改动**，会问一句：确定 = 保存后关闭，取消 = 放弃改动并关闭 ——
  以前点了「取消」改动就**悄悄没了**；
* 保存成功后会给明确反馈（「对阵已保存：N 场（用户端已刷新）」），用户端当页同时换新，
  不必等广播；
* 「恢复默认对阵」＝请服务端按分组算法重排，放弃手改。

#### 弃权（没人到场 / 人数不足）

长期没人到场或人数不足时，在对局卡（或对阵图）上点 **弃权**，选是哪一方弃权即可：

* 弃权方**名次垫底且不能获胜**，对手**直接晋级**；淘汰赛的对阵图会顺着自动推进
  （实测 `WB-1-1` 判弃权后，胜者立刻出现在 `WB-2-1`）；
* 3~4 队同场时只把弃权方移出名次竞争，其余队伍继续把这场打完；
* 备注里留一条 `[弃权] A队 原因 → B队 晋级`，对局卡上该方显示「弃权」并加删除线；
* 点「重置」即可撤销（比分、名次、弃权标记与那条备注一并清除）；
* 队伍人数少于 `team_size` 时，诊断面板会提示可以直接判弃权。

#### 替补规则

**替补不是选手的一种类别**：名单里没有「替补选手」，谁上场由**每场比赛**决定
（见下文「对局替补」）。因此：

| 赛制 | 替补 |
| --- | --- |
| 积分制 | **允许**：按均分排名，替补上场同样计入本人成绩；缺人时逐场安排即可 |
| 锦标赛制 | **不提供**：固定队伍全程不换人（要换整队请用「队伍换人」） |

### 操作流程（管理端）

| 步骤 | 积分制 | 锦标赛制 |
| --- | --- | --- |
| 1. 选赛制 | 新建届时选，或「赛制」面板切换 | 同左 |
| 2. 参与名单 | **从成员列表勾选**参赛的人（缺档案自动建好；未指定 = 全员参与；全不选保存 = 本届无人参与） | 同左 |
| 3. 创建分组 | —— | **快速创建分组**（一键组队 + 排赛程，带结构预估）；也可分步用「随机组队」→「生成赛程」 |
| 4. 录入结果 | 逐局结算，实时更新积分榜 | 填轮次或本场成绩，自动判定晋级与败者组 |
| 5. 缺人处理 | 在赛程里点某位选手 → **安排替补**（三档范围）；空位可补人 | 在对局上点**弃权**，对方直接晋级 |
| 6. 直播 | 每场可开推送与提示；选手名单里可复制推流地址 | 同左 |
| 7. 追加 / 清空 | 追加补赛、追加空局；也可清空全部比赛重来 | 清空全部比赛后重新生成 |

对应接口：

| 接口 | 赛制 | 说明 |
| --- | --- | --- |
| `POST /api/format` | 两者 | 切换赛制（会清空赛程） |
| `POST /api/participants` | 两者 | 保存参与名单（空数组 = 本届无人参与；保存过即为显式名单） |

| `POST /api/teams/auto` | 锦标赛 | `{teamSize, mergeRemainder, seed}` 随机组队（会清空赛程） |
| `PUT /api/teams` | 锦标赛 | 手动调整队伍（结构变化会清空赛程） |
| `POST /api/tournament/preview` | 锦标赛 | **只读**预估结构 `{teamSize, groupCount, size, teamsPerMatch, loserBracket}` |
| `POST /api/tournament/generate` | 锦标赛 | `{size, teamsPerMatch, loserBracket, reform, teamSize, groupCount, seed}` |
| `POST /api/rounds/{ref}/result` | 两者 | `{sets, sides, winner, durationMinutes, startedAt, finishedAt}` |
| `POST /api/rounds/{ref}/walkover` | 两者 | 判一方弃权 `{side, reason}`，其余各方自动晋级 |
| `POST /api/rounds/{ref}/live` | 两者 | 本场直播开关 `{enabled, note}`（接口保留，界面不再暴露开关） |
| `POST /api/rounds/{ref}/times` | 两者 | 计划 / 开始 / 结束时间 |
| `POST /api/rounds/{ref}/reset` | 两者 | 重置一场（清比分 / 名次 / 弃权留痕；锦标赛连带回退下游） |

### 用户端展示「比赛规则」

用户端（总览页底部、以及只读查看某一届时）有一个**比赛规则**面板。它的内容不是另写一份文案，
而是**由当前赛制与参数实时推导**（后端 `logic.rulebook`）。两条硬要求：

* **一个字的文案都不入库**：改了赛制 / 人数 / 同场队伍数 / 计分口径，这里整套跟着换，
  不会出现「规则说的和实际打的不一样」；
* **能算出具体数字就算出来**：每队打几场、几个组、每组几队、每场几队同场、淘汰赛几轮，
  全部按**当前实际的队伍与赛程**推（还没生成赛程时给「下一步做什么」的说明）。

三条「文案对错」上的硬规矩（`tests/test_rules_text.py` 盯着，都属于看一眼就懂的错）：

* **以实际为准，不并列两个数**：配置写 4 队同场、赛程里排出的是 3 队同场时，规则只说
  「每场 3 队同场」——以前会写成「4 队同场（每场 3 队同场）」，看的人只会觉得规则自己都没想清楚；
* **单败就别说败者组怎么打**：一句写死的「默认双败」放到单败的届里就是假话；
* **不写旁白**：「（完全确定，无随机）」「（不需要人工点胜负）」「（每个组的人数可调）」
  这类话是写给开发者的，用户读的规则里不该出现。

**加粗在服务端渲染**：规则条目里的 `**…**` 由 `markdown.inline()` 转成 `<strong>` 再下发
（先转义、后按同一套白名单渲染）；同时另发一份**摘掉标记的纯文本**（`items`）给群消息
摘要与卡片渲染——卡片是往图上画字，`**` 会原样印出两个星号。两份都在服务端出，
前端与下游都不需要自己处理 Markdown。

面板分成五块，覆盖「怎么打、怎么判、怎么出线、怎么淘汰」的全过程：

| 分块 | 讲了什么 |
| --- | --- |
| 赛制概览 | 赛制（积分制 / 锦标赛制）、参赛人数与队伍数、每场形式、小组赛 → 淘汰赛 → 冠军的流程 |
| 分组与小组赛 | 几个组、每组几队、**单循环还是 N 队同场**、每队打几场、每场名次分表（2 队即 2/1，3 队即 3/2/1，4 队即 4/3/2/1）、小组排名依据、平局规则、**出线名额与被淘汰的队数** |
| 淘汰赛 | 规模（N 强）、逐轮名称、「对阵固定为 2 队一组」、**怎么淘汰**（单败输一场即走 / 双败输两场才走）、**怎么晋级**（胜者进下一轮、败者进败者组）、总决赛与冠军归属 |
| 排期与录入 | 多轮录入、大比分与总成绩怎么算、弃权怎么判、改期与重置的影响 |
| 其他 | 计分口径（类型 / 标签 / 判断标准，含「0 是合法成绩」这类约定）、直播、单轮目标分 |

顶部还有一行参数速览（赛制 / 计分 / 判定 / 参赛 / 每队 / 每场 / 分组 / 淘汰 / 出线 …），
末尾附上管理员在「赛事信息 → 补充说明」里填的自由文案（选填，**出厂为空**——
规则主体已经在上面自动写好了，这里只说组织者想补充的话）。

对应关系举例：

| 参数 | 规则面板里的呈现 |
| --- | --- |
| `teamsPerMatch = 3` | 「打法：**3 队同场**——每轮把组内队伍尽量凑满一场…」「每场名次分：第 1 名 3 分、第 2 名 2 分、第 3 名 1 分」 |
| `teamsPerMatch = 2` | 「打法：组内**单循环**——同组每两支队伍恰好相遇一次，共 3 轮，每队 3 场；奇数队时每轮有一队轮休」 |
| `loserBracket = false` | 「8 强单败，逐轮 八强 → 半决赛 → 决赛」「输一场直接淘汰，没有败者组」 |
| `loserBracket = true` | 「双败：胜者组输一场掉进败者组，再输一场才真正淘汰」「胜者组冠军 vs 败者组冠军打总决赛」 |
| `allowDraw` | 「小组赛允许平局」/「小组赛必须分出胜负（不设平局）」 |
| `minRankPlayed` | 「出场不足 4 局不参与名次」 |
| 赛制切到积分制 | 「没有淘汰与晋级：打完所有局，按均分排名」 |

管理端的「赛制」面板底部也内嵌了同一份预览，改完参数能立刻看到用户端会显示什么。

## 隐私与推流地址

### QQ 头像怎么取、怎么刷新

前端不直接引用 QQ 头像域名（防盗链 / 混合内容 / 暴露 QQ 号），统一走
`/api/avatar/p/<选手 ID>?size=100`，由服务端去抓：

* 三级缓存：**内存 10 分钟** → **磁盘 12 小时**（`data/avatar_cache/<QQ>_<尺寸>.<ext>`）
  → **浏览器 1 小时**（`Cache-Control: public, max-age=3600`）；
* 磁盘缓存过期后会重新回源，因此**在 QQ 里换过头像最多 12 小时自动跟上**；
* 想立刻看到新头像：管理端选手卡 / 选手名单里点 **「刷新头像」**——
  它会带 `?refresh=1` 跳过内存与磁盘缓存强制回源，并给图片地址加时间戳绕过浏览器缓存；
* 回源失败时优先用磁盘上的旧图兜底（`stale`），实在没有才用生成的占位图
  （按 QQ 号取色的六边形 + 名字首字）；响应头 `X-NTE-Avatar` 会说明这次数据来源：
  `memory` / `disk` / `fetched` / `stale` / `placeholder`，排查时先看它；
* 没配 QQ 的选手接口返回 404，前端会把坏图移除、露出「首字」兜底，不会出现破图图标；
* 上传自定义头像（管理端选手行里的「头像」）**优先级高于 QQ**（图存在统一的内容仓库里，
  与通知 / 信息里的插图共用一份：同一张图不会因为「既当头像又当插图」而存两遍），
  此时前端根本不会再请求 `/api/avatar/p/...`；
* 抓取只认图片魔数（JPEG / PNG / GIF / WebP / BMP），并按真实格式落盘——
  早期版本会把 GIF 存成 `.svg`，读回来的 MIME 与内容不符，浏览器直接不显示。

### 用户端只看得到名字与头像

选手的 **UUID / QQ / 推流流名 / 推流地址**一律**不下发用户端**（公开状态、
WebSocket 广播、`/api/live/info` 里都没有），管理端在登录后通过
`GET /api/private` 单独获取。公开状态里的选手对象只有这些字段：

```json
{ "id": "p01", "name": "甲", "avatar": "", "tag": "NTE-07",
  "substitute": false, "active": true, "hasStream": true, "hasAvatar": true,
  "memberUid": "3f2a…" }
```

* 头像改为 **`/api/avatar/p/<选手 ID>`**，由服务端去查 QQ —— 客户端请求里不会再出现 QQ 号；
* `memberUid` 是该选手**关联的全局成员**（可空 = 独立选手），仅用于展示封禁状态与关联，
  不含任何账号凭据；
* 选手搜索、选手卡、组队台、积分榜等只显示**姓名 / 编号 / 停用**；
* 界面配置里的「显示 QQ 号」开关已移除（QQ 永远不展示）；
* 「显示选手头像」开关保留。

### 推流一种、观看两个地址

**推流只有 WHIP**（WebRTC / UDP）；**观众看直播就是两个地址**，打开即可观看，
播放器用的也是它们（不是「播放页 / 播放列表 / 内嵌」几种说法）：

| 用途 | 地址 | 传输 |
| --- | --- | --- |
| 推流 | `https://…:8889/<流名>/whip` | WHIP / UDP |
| 观看 | `https://…:8889/<流名>` | WebRTC / UDP，延迟 ≈1s |
| 观看 | `https://…:8888/<流名>` | HLS / TCP，延迟 2~10s，抗抖动 |

* 地址只在端口上按流名区分——**`/whep` 只出现在「信令」这一层**：页面上/分享出去的
  地址是 `https://…:8889/<流名>`（MediaMTX 自带的播放页），而播放器跑 WebRTC 时
  往 `https://…:8889/<流名>/whep` 发 SDP 换答案（MediaMTX 的读流端点，它自带播放页
  用的也是这个）。**别把裸路径当信令端点**：对它 POST 拿到的是 Go 路由的
  `404 page not found`（跟随便编个路径一模一样），看着像「没人在推流」，其实是发错了地方：
* 观众可以在播放器上方自行切换走 8889 还是 8888 那条；
* **两个观看地址都是 HTTP 系，必须 HTTPS**：站点上 CDN 后是 HTTPS 页面，
  源站用 `http://` 会被浏览器按混合内容拦掉；
* **出厂不预填地址**，要在「服务器管理 → 直播配置」里按自己那台媒体服务器填。
  新装时各处会明确提示「未配置」，不会静默失败——预填别人的域名比留空更糟：
  看起来配好了，其实连的是别人的服务器；
* 推流与观看覆盖**同一批流名**，因此选手只要在 OBS 里配一次 WHIP 地址，整届都不用改；
* **推流地址属于凭据**，只在管理端出现（`/api/private`），公开状态里只有观看地址；
* 「直播地址」弹窗列出**本场每位选手**的推流地址与两个观看地址，都带复制按钮；
* **直播配置表单读的是私有配置**（`/api/server/config` 里的 `stream`，仅服务器管理员）——
  公开状态里的 `stream` 是脱敏白名单，不含根地址，拿它渲染表单会出现空输入框；
* **API 密码像别的凭据一样「只存服务端」**：接口只回 `hasApiPass` 布尔，表单值恒为空
  （显示「已配置（留空 = 不修改）」）。留空 = 保持原值，要清空得勾「清除已保存的 API 密码」。
  以前 `/api/private` 直接 `stream.dump()` 把明文下发了，而那个接口**赛事管理员就能读**，
  等于把媒体服务器的控制密码交给每一位赛事管理员——现在两处共用
  `logic.management_stream_config`，不会再各漏一次；
* **直播配置整块只有服务器管理员能改**（`/api/config` 里的 `stream` 补丁一律 403 给
  其他人）——它全是站点级设置，而且直播连总开关都没有，赛事管理员这边一个可改的字段都不剩
  ——前端藏表单不算数，闸门在服务端（见 `_apply_stream_patch`）。

> 历史配置里那两个 `http://live.shiyora.net…` 旧默认值会在加载时**自动升级为 https**
> （只认这两个旧 host，自定义地址一律不动）。若媒体服务器还没开 TLS，
> 在「直播配置」里把地址改回 `http://` 即可。

> 早期还支持 RTMP / RTSP / FLV 推流与「网页内嵌」播放，现已**整条链路移除**：
> 数据库里的对应列会在启动时自动删掉，历史 `mode = flv / embed` 会回落到 `auto`。

### 推流建议：只用 WHIP，别开 B 帧

管理端**凡是有「复制推流地址」的地方**（本场直播弹窗、选手名单、直播页）都会提醒这两件事：

* **推流用 WHIP**（WebRTC / UDP）：延迟最低、弱网下表现最好，OBS 30+ 原生支持。
  协议表里的「优先」标记、播放线路切换上的「优先」角标，以及
  **默认播放线路 `auto`（先试 WebRTC，不通再退 HLS）**都是这个取向；
* **OBS 里把「B 帧 / B-frames」设为 0**，关键帧间隔 2 秒，编码器用 H.264。
  B 帧要靠后续帧才能解码，而 WebRTC / WHIP 是逐帧实时发送的，
  开了 B 帧最容易出现花屏、抖动，甚至直接推不上去（HLS 观看侧同样受影响）。

复制推流地址后会弹一条提醒（9 秒），按钮的悬浮提示里也带着同一句话。

### B站 直播（源站直嵌，不经本站）

成员也可以**同时在 B站 开播**。填了 B站 直播间号之后，他在播时会在直播页多出**一路机位**
（粉色「B站」徽标），画面是 **B站 官方外链播放器直接嵌进来的**，跳转链接一并给出。

**要填什么：只填一个「B站直播间号」**

打开自己的 B站 直播间，**地址里那段数字就是房间号**（`live.bilibili.com/12345` → `12345`）；
短号也认。填的时候：

* **纯数字、整条直播间链接、甚至带说明文字都能识别**（只抠数字）——直接粘链接最省事；
* 填了非数字的文字会**当场报错**，而不是静默清空（否则你会以为填上了却一直没生效）；
* **填完立刻校验一次**：房间号不存在会直接告诉你「B站 查不到这个直播间」；
  正在直播则回一句「正在直播：《标题》」；B站 接口不可达时只说「暂时无法确认」，
  **绝不因此拦住保存**（第三方抖动不该让人存不了资料）。清空房间号即取消这一路。
* 填哪儿都行：服务器管理员在「服务器 → 成员管理」里代填，或成员自己在
  「我的 → 我的直播间」里填。

> 除了房间号，**什么都不用填**：B站 侧的推流仍然由成员自己用直播姬 / OBS 推到 B站，
> 本站不需要（也不该拿到）他的 B站 账号、密钥或推流码。

**开播后自动同步（标题等）**

成员在 B站 一开播，下面这些都会**自动**从 B站 取来显示，他不需要在站内再维护一遍：

| 同步什么 | 显示在哪 |
| --- | --- |
| **直播标题** | 直播页对阵条（`B站直播 · 名字：《标题》`）、机位悬浮提示、右侧「播放地址」面板、成员卡的那一行副标题、群消息 |
| 主播名（B站 昵称） | 播放地址面板 |
| **在线人数** | 对阵条（`1024 人在看`）、播放地址面板、群消息 |
| 分区 | 对阵条与播放地址面板 |
| **开播时间** | 对阵条与播放地址面板（`2026-10-05 20:10 开播`） |

同步跟着**探测节奏**走（20 秒缓存，由直播页的轮询顺带刷新），所以改标题 / 改分区之后
最多几十秒就会跟上；成员卡上那行副标题在开播期间显示的就是 B站 的标题，
**下播后自动恢复**成他自己填的直播间名字。

* 展示：直播页的机位条里多一路「B站直播」（粉色徽标）；选中后舞台里嵌的是 B站 官方播放器，
  播放器下方的对阵条位置会写「B站直播 · 名字：《标题》· 分区 · N 人在看」并提供跳转；
  右侧「播放地址」面板给的是 **B站直播间号 + 跳转地址**（没有本站的推流 / 观看地址）。
* 群里：`比赛直播` 那条也会列出 B站 那一路（含标题与在线人数），并附上直播间链接。

**怎么实现的（以及刻意不做什么）**

* 只做两件事：① 用 B站 **免登录**接口 `room/v1/Room/get_info` 判断 `live_status`
  （1 = 直播中；0 未开播、2 轮播都不算）并顺手带回标题 / 在线人数 / 分区 / 开播时间。
  **主播名不在这里**——那个接口只给 `uid`，所以只在**在播**时再问一次
  `live_user/v1/UserInfo/get_anchor_in_room`（没开播的人不必为一行字多打一次请求）；
  开播时间字段 B站 换过格式（早期是秒级时间戳字符串，现在是 `2026-10-06 11:42:42`
  这种日期文本），**两种都认**——只认一种的话，另一种就是界面上永远空着、还看不出为什么的一行；
  ② 把官方播放器
  `https://www.bilibili.com/blackboard/live/live-activity-player.html?cid=<真实房间号>`
  嵌进舞台（关掉弹幕 / 水印 / 互动区，要看这些点「在 B站打开」）。
  填的是短号也没关系：探测按填的号，播放器与跳转地址一律用 B站 返回的**真实房间号**
  （`cid` 只认真实号）。
* **视频流一概不经本站**：不中继、不转码、不代理，也不做鉴权——B站 那边谁能看由 B站 说了算。
* **探测结果只读缓存（20 秒）并跟着后台刷新走**，所以请求路径永不等待 B站；
  和 MediaMTX 那套**完全独立**：B站 接口挂了只是「不知道自己这边谁在播 B站」，
  跳转链接照旧给、其余直播功能一律不受影响（`known=false` 时界面上直说「无法判断」，
  绝不显示成「没有人在播」）。
* 「**明确没有这个直播间**」（B站 回 `-400`）与「**探测失败**」是两件事：前者是确定的答案，
  会直接告诉填的人「房间号可能写错了」；后者只能说「暂时无法确认」。
* **不进站点级直播配置**：房间号是**成员**身上的属性，不是媒体服务器配置（因此
  `StreamConfig` 里没有相关字段，写 `stream` 补丁也改不到它）。

### 用户端看直播：先选比赛，再选机位

直播页播放器上方是两行选择器：

1. **比赛**：列出**本届全部对局**（不限于正在进行的那场），**进行中**的排最前（带 LIVE 点），
   每个比赛后面标着这场有几路机位（没配流名的标「无机位」）；点「全部机位」可跨比赛看。
   选中一场后会自动切到该场的第一个机位；
2. **机位**：该场比赛的选手机位（选手头像 + 名字），点击即切换播放。

**有人在推流就直接开播**（比赛直播页与成员频道页都是）：进页面时自动挑第一路在播的信号并
连上，**对方在你打开页面之后才开播也会自己出来**（每次重绘都会试一次，`playRoom` 幂等，
同一路正在播只恢复画面、不重连）。播放器初始**静音**——浏览器的自动播放策略只允许静音的
自动播放，要听声音点播放器上的音量图标即可。唯一不自动播的情况是你自己按过「停止」；
之后点任意机位 / 点「播放」就会恢复自动开播。

赛程页每张**有机位**的对局卡上还有一个公开的
「**看这场直播（N 路机位）**」按钮：点它直接切到直播页并选中该场，不用自己翻列表。
机位数量以该场出场选手为准（与后端下发的 `rounds[].streams.cast` 一致）。

「谁在推」由**选手流名**决定（整届固定），「看哪场」由**比赛编号**决定，两者互不影响：
选手只要推自己的地址，观众在页面上按比赛挑就行。

### 播放线路（WebRTC / HLS）

播放器上方还有 **线路** 切换，选择会记在浏览器本地：

* `WebRTC`：走 8889，延迟最低（默认）；
* `HLS`：走 8888，抗抖动；Safari 用原生播放，**Chrome / Firefox 自动加载 hls.js**
  （CDN，按需加载；取不到就只能改用 WebRTC 线路）；
* 不选 = 跟随管理端配置的默认线路。**`auto` 的兜底顺序是 WebRTC → HLS**。

管理端「信号探测」分别探测 WebRTC 与 HLS **两个地址**，失败时给出可照做的原因
（证书校验失败 / 协议与端口不匹配 / 超时 / 连接被拒），比原来的底层英文报错好排查。

> **探测是服务端常驻的：没人访问也一直在探**（`live.watch_loop`）——这样任何页面一打开，
> 读到的都是刚探回来的结果，而不是「等你来了才开始探」。间隔是**自适应的**：
> 有人在播 / 有页面开着时 5 秒一次，没人播也没人在线时放宽到 20 秒（**放宽不是停**），
> 探测失败则 2 秒后重试（不能用空闲间隔去等，那等于媒体服务器一抖就瞎 20 秒）。
> 单轮整体还有 12 秒超时兜底，超时就跳过这一轮，绝不让循环挂住。
>
> **请求路径永远只读缓存、一秒都不等它**：`/api/live/health` 与 `/api/state` 立刻返回手里的值；
> 前端在直播 / 频道页仍会轮询（**有人在播 20 秒一次、没人在播 60 秒一次**，比从前放宽——
> 因为推送已经把「即时」做掉了），标签页切走 / 离开页面即停。
> 用户打开页面时服务端顺手 `kick_refresh` 催一次，而**刚探过就跳过**（不与常驻循环抢活）。
>
> **状态变化通过 WebSocket 推给在线客户端**（`{"type":"live"}`，与 `/api/live/health` 同一份数据）：
> 开播 / 下播几乎当场可见，全站任何页面的「直播中」标记都跟着变，而**正在播的画面不受影响**
> ——前端只在「谁在播」真的变化时才重绘，视图签名没变就不重建播放器（线路切换同理）。
> 检测过程在界面上是一段加载动画；连续 3 次拿不到就显示「获取失败，等待服务器修复」，
> 不再自动重试，等用户手动点「重试」。需要立刻拿最新结果时传 `?probe=1` 现场重新探测一次。
>
> 一轮探测的实际开销很小：推流列表是媒体服务器的**本地** HTTP（几十字节，5 秒一次可忽略），
> 端口探测有 60 秒 TTL、B站 开播状态有 20 秒 TTL，所以它们并不会每轮都真发请求。
> 部署上要注意：常驻探测是**按进程**跑的，别用多 worker 起同一个站点（每多一个进程就多一份探测）。
>
> **端口探测只探 HLS 服务的根地址**：去请求任何具体流路径都会让媒体服务器为那个路径
> 建一个 HLS 会话，没人直播时日志里就会不停刷 `no stream is available on path '…'`。
> 探根地址一样能验证端口与证书（返回 `404` 也算端口通），但不会产生任何会话。

管理端的「复制推流地址」复制的是当前机位的 WHIP 地址（推流只有这一种）。

### 推流标识：按对象各自的流名 / 推流 ID

| 对象 | 标识 | 例子 | 说明 |
| --- | --- | --- | --- |
| 选手 | 他自己的流名 | `tom` → `…:8889/tom/whip` | **整届固定**，换比赛不用重推 |
| 成员直播间 | 成员的 `streamId` | `tom` → `…:8889/tom/whip` + **Bearer 令牌** | 令牌是 OBS 里单独的「Bearer 令牌」字段（见「成员、权限与服务器管理」） |
| 遗留频道 | 频道流名 | `room1` → `…:8889/room1/whip` | 管理员手工建的传统频道，按登记白名单放行（无令牌） |

**没有按比赛编号的推流地址**：直播只按选手区分。哪台机位对应哪场比赛是
「组织信息」（由该对局出场的选手决定），观众在直播页按比赛筛选机位即可。

* **全部是源站地址，本站不做反代**：播放器与观众浏览器直接连媒体服务器；
* **两个观看地址（公开）**：`<base>/<流名>`（8889）与 `<hlsBase>/<流名>`（8888），
  随公开状态下发（`rounds[].streams.play`、`state.streams[<选手>]`）；
  浏览器会向媒体服务器发跨域请求，MediaMTX 默认回 `Access-Control-Allow-Origin: *`，
  无需额外配置；
* 直播页的「打开源页」按钮就地打开当前线路那一条（MediaMTX 自带的播放页）；
  **播放器走 WebRTC 时对 `<base>/<流名>/whep` 发信令**（MediaMTX 的读流端点），
  只有 404/405（这个端点不存在）才退回裸路径——两种版本都不用改配置；
* 选手未在任何对局中时同样是这个地址（与比赛无关，因此没有「回退」一说）。

> **HTTPS 站点必须配 HTTPS 源**：页面是 HTTPS 而源站是 `http://` 时，
> 浏览器会按混合内容把 WebRTC 信令请求**直接拦掉**（控制台会报
> `Mixed Content`），这与本站无关，只能把源站也换成 HTTPS。
> 自签名证书同样不行——观众侧需要浏览器信任的证书（管理端的「信号探测」可以
> 关掉校验，但那不影响观众）。

### MediaMTX 侧需要开的东西

```yaml
# mediamtx.yml
webrtc: yes          # 8889，WHIP 推流 / WebRTC 观看
webrtcAdditionalHosts: [live.shiyora.net]   # 公网 IP/域名，否则浏览器拿不到候选地址
hls: yes             # 8888，HLS 观看
hlsVariant: lowLatency  # 想要更低延迟可开 LL-HLS
api: yes             # 9997，控制 API：本站用它查「谁真的在推流」
apiAddress: :9997
# —— 站点是 HTTPS 时这几项必不可少（否则浏览器按混合内容拦截）——
certFile: /path/fullchain.pem    # 受信任证书（Let's Encrypt 等）
keyFile: /path/privkey.pem
hlsEncryption: yes               # HLS 走 https://…:8888
webrtcEncryption: yes            # WHIP 推流与 WebRTC 观看走 https://…:8889
```

* 管理端「直播配置」里填两个根地址：WebRTC `https://…:8889`、HLS `https://…:8888`；
* MediaMTX 的 **HLS 与 WebRTC 是两个独立端口**（8888 / 8889），别把 HLS 地址
  填成 WebRTC 端口——管理端的「信号探测」会分别探测两个地址并给出原因；
* 媒体服务器上记得**开启推流鉴权**——推流路径就是播放路径，
  仅靠路径保密不足以阻止他人推流（见下一节）。

### 推流鉴权：流名登记 + 成员令牌（不接受匿名推流）

默认情况下媒体服务器**谁都让推**：只要知道路径，任何人都能往 `…/<流名>` 推流，
而推流路径与播放路径又是一回事（推送方向由客户端行为决定）。要把它收口成
「**流名已登记，且成员令牌匹配**」，就让媒体服务器每次推流都来问一次本站（HTTP 鉴权回调）：

```yaml
# mediamtx.yml —— 只放行本站登记过的推流
authMethod: http
authHTTPAddress: https://<本站地址>/api/live/auth
authHTTPExclude:            # 播放不回调，避免每个观众都打一次本站
  - action: read
  - action: playback
```

本站的 `POST /api/live/auth`（MediaMTX 会带上 `action / path / protocol / ip / user…
`）判定：

| 动作 | 判定 |
| --- | --- |
| `publish` | **成员推流**必须「路径 = 他的 `streamId`」**且** Bearer 令牌匹配，并且未处于封禁期，否则回 `401`；主直播间与管理员手工建的遗留频道见下条 |
| `api` | 按「直播配置」里的 API 用户名 / 密码校验（没填就放行，与以前一致） |
| `read` / `playback` / `metrics` / `pprof` | 放行（播放建议直接在媒体服务器侧用 `authHTTPExclude` 排除，不必回调） |

**推流标识（流名 / 推流 ID）与推流令牌只收 ASCII**：字母、数字、连字符(`-`)、下划线(`_`)。
中文、空格与全角字符会被**当场拒绝**（回 400 并说明原因），而不是静默丢掉字符——
静默清洗会存成另一个值，用户照着填的地址推不动，反而更难查。
（旧版 `clean_key` 用 `str.isalnum()` 判字符，而它对中文也返回 `True`，于是中文流名能存进去；
升级后启动日志会点名这些历史数据，规则页里也会提示，但不会拒绝启动。）

**主直播间与遗留频道**是例外：它们的流名不属于任何成员，没法「按成员认人」。
默认仍是「流名登记过就放行」（`stream` 这种流名人人都知道，实质上等于不设防）；
要收口就在「服务器 → 直播配置 → **推流令牌**」里设一个值，此后推这些流名也必须带它
（`?token=` 或 Basic 认证）。**留空 = 保持旧行为**——升级不会把正在推的主直播间掐掉；
令牌按 UTF-8 字节做常量时间比较（含中文也不会把接口打成 500）。

**推流凭据 = 推流 ID + Bearer 令牌**（成员在 `/user` 或服务器管理员在 `/admin` 里取得）。
OBS 的 WHIP 输出把这两样分成两个字段填：

| OBS 字段 | 填什么 |
| --- | --- |
| 服务 | `WHIP` |
| 服务器 | `https://live.shiyora.net:8889/<streamId>/whip`（**不带令牌**） |
| Bearer 令牌 | 成员自己的 `bearerToken` |

* 令牌由 OBS 以 `Authorization: Bearer` 头随 WHIP 请求一起发出，服务端用**该成员的
  加盐哈希**做常量时间校验（同时也接受 `?token=` 写法）；
* 路径还会先查**封禁**：命中全局 / 本届封禁（或成员被停用）一律拒绝，理由写进日志；
* **成员推流强制双凭据**；主直播间（默认流名）与服务器管理员手工建的**遗留频道**仍走
  登记白名单（无令牌），以兼容既有直播。若要把遗留频道也收紧，给它们建对应成员即可。

注意事项：

* 打开后**就没有匿名推流**了：流名未登记、或成员令牌不符，一律推不上；
* 代价是**耦合**：本站不可达时媒体服务器会拒掉推流（这正是白名单的语义），
  所以本站要尽量保持在线；
* 本站日志会记下每次推流鉴权的结果（通过 / 拒绝 + 路径 + 原因 + IP / 用户名），
  「谁推不上」先看它；
* 流名本身会出现在公开观看地址里（`…/<流名>`），因此**只有流名是不够的**——
  成员推流还需要正确的 Bearer 令牌，令牌可随时在 `/user` 或 `/admin` 里轮换。

### 流名唯一性（自动查重）

推流流名必须每位选手互不相同，否则两人会推到同一个地址（串流）：

* **保存时拦截**：`POST /api/players` 与 `PUT /api/config`（批量保存选手名单）
  都会先查库，重复直接回 400 并指出是哪两位选手；
* **诊断兜底**：`/api/diagnostics` 与配置校验会对历史数据里已有的重复流名给出提示；
* `/api/private` 的 `duplicates` 字段也会列出重复项，管理端可据此排查。

## 成员频道（日常直播）

比赛之外，群友也能在这里常驻开播。入口是顶栏的 **「频道」** 页，**与赛事届次无关**：

**成员直播间（自动出现）**：成员只要在 `/user`（或服务器管理员在 `/admin`）里设置了
**推流 ID** 或 **B站直播间号**，他的直播间就**自动出现在频道页**——无需管理员添加或审批；
一旦真的开播（媒体服务器上报，或探到他在 B站 直播），就点亮「直播中」。成员可自行改
直播间名字；若他此刻在参加比赛，直播间卡上会显示「比赛中 · <对局>」；被封禁则显示封禁
时间与理由。本站推流走「推流 ID + Bearer 令牌」（地址见上一节的表格），B站 那一路
则**直嵌 B站 官方播放器**（视频不经本站，播放条上只有「在 B站打开」）。

> **没开播的不列出来**：频道页那条**选择条**只列**此刻真在播**的房间（比赛直播页同理）。
> 打开这一页是「来看谁在播」，不是来看花名册——一堆没开播的房间会把真正在播的那几个
> 挤到后面，还得自己一个个点。所以「有人开播了再显示」：他一开始推流（或 B站 开播）
> 就自动出现（服务端常驻探测发现后**当场推给页面**，不用刷新），下播就自动收起来。
> **管理员也一样**：他要管理 / 封禁 / 改公告就点下面那条**频道卡片**目录，那里仍然
> 列全量，没开播的卡片上标着「未开播」——但选择条不替谁占位。
> 直接打开某个**没开播**频道的链接（`/channels/<流名>`）也能看，页面上会写「当前未开播」。

> **「在播」有两条链路**：本站推流（MediaMTX 上报 `ready`）与 **B站 直播**（服务端探到
> `live_status=1`），任一条在播就算在播——头像光环、成员卡的「直播中」、主页「N 个在播」、
> 频道页选择条、**比赛直播页的比赛条与机位数**都按这个口径算（所以有人在打比赛且用 B站
> 直播时，那一场也会带着他的机位出现在比赛条上）。

**传统频道（管理员手工建）**：也可以在「频道」页手动新增 / 编辑频道，用于没有对应成员账号的机位：

* **只有服务器管理员能改**：频道与「频道公告」都是**全局**资源（跨届共享），
  所以新增 / 编辑 / 删除 / 改公告都要求服务器管理员——赛事管理员只管自己那一届，
  不该动别人的常驻频道（否则等于跨届越权）。成员直播间不在此列：那是本人资料的一部分；
* **常驻、跨届**：频道存在同一个库里，但**不属于任何一届**——没有比赛时照样能播，
  开赛锁定、只读查看某一届都照看不误（频道页是独立路由，与届次无关）；
* **推流标识还是流名**：每位频道一个流名（在「频道」页新增 / 编辑时填写），
  地址与选手同一套规则（`https://live.shiyora.net:8889/<流名>/whip`），常驻固定；
* **流名全局唯一**：与**选手**、**成员**以及其它频道都不能重复，保存时即拦（否则会串流）；
* **在播判定同一套**：只有媒体服务器上报 `ready` 的频道才标「直播中」
  （见上文「谁真的在推流」），探测不到就一个都不标；
* **隐私一致**：QQ / 推流地址只在管理端（`/api/private`），
  头像走 `/api/avatar/c/<频道 ID>`，客户端请求里不会出现 QQ 号；
* 频道卡支持 **标题 / 游戏区服 / 常驻角色 / 简介 / 标签 / 外部链接 /
  置顶推荐 / 排序 / 停用**；停用的频道对访客隐藏，管理员仍可见并重新启用；
* **频道公告**：板块顶部有一段**全局可编辑**的公告（管理端「编辑公告」→
  `PUT /api/channels/notice`），用来放异环相关的说明 / 活动文案；同样与届次无关。

> 异环目前**没有面向第三方的官方数据接口**，因此与异环相关的内容
> （区服 / 常驻角色 / 公告 / 标签）都是**管理员自行填写**的展示信息，
> 本站不会自动抓取游戏数据，也不做任何猜测。

对应接口：

| 接口 | 说明 |
| --- | --- |
| `POST /api/channels` | 新增 / 更新成员频道（需登录；校验流名全局唯一） |
| `DELETE /api/channels/{id}` | 删除成员频道（需登录） |
| `PUT /api/channels/notice` | 设置频道公告（全局，需登录） |
| `GET /api/avatar/c/{id}` | 频道头像（服务端代理 QQ，客户端看不到 QQ 号） |

公开状态里带 `channels`（每人的播放地址与展示信息）与 `liveChannels`
（正在推流的频道 ID）。播放器复用直播页那一套（WebRTC 优先、HLS 兜底），
两个板块各持一个播放器实例，互不打断。

## 本届参与名单

报名池（选手名单）是长期名单，可以先把所有人都录进来；**每一届再单独勾选真正参赛的人**。

* 管理端 → 「本届参与名单」：勾选 / 全选 / 全不选 / 反选，然后保存
* **从未保存过**时视为**全员参与**（旧数据无需迁移，行为与以前一致）
* **保存过就按保存的那份算**：全不选后保存 = 本届**无人参与**，不会再变回全员
  （这正是「清空名单却变成全选」的修复点）；参与名单为空时现有赛程原样保留，
  诊断面板会提示「未开赛对局里还有非参与选手」
* 未参与的选手会被排除在组队之外，并在选手卡 / 组队台上标注「未参与」

## 比赛与赛事的时间

界面上始终能看出**「是否已结束」以及「何时开始 / 何时结束 / 用时多久」**，两层时间都由管理员维护。

### 比赛（对局）时间

每场比赛有三个时间字段：`scheduledAt`（计划）、`startedAt`（开始）、`finishedAt`（结束）。
服务端据此推导出 `timeState`（供前端直接渲染，两种赛制一致）：

| timeState | 条件 | 界面显示 |
| --- | --- | --- |
| `finished` | 已结算，或已登记结束时间 | `10/03 20:05 → 20:47` + `用时 42 分钟` |
| `running` | 状态为进行中，或已登记开始时间 | `20:05 开始` + **`结束待定`** |
| `scheduled` | 未开始但已排计划时间 | `计划 10/03 20:00` |
| `unscheduled` | 三者都没有 | `时间待定` |

* **正在进行中的比赛 = 开始时间 + 可选的结束时间**：只填开始时间即为「进行中 · 结束待定」，
  结束时间留空、随时可补。
* 管理端每张对局卡片都有「时间」按钮：可单独编辑三个时间，带「计划/开始/结束=现在」与「清空全部」。
* 录入比分弹窗里也能直接填写开始 / 结束时间；留空则用保存时刻自动补全。
* 登记结束时间**不会**自动结算——胜负仍由比分决定，否则会出现「已结束但没有胜者」的对局卡住淘汰赛推进。
  这种情况下界面会标出「已结束 · 比分待录入」，接口也会回一条提示。
* 开始时间若早于结束时间之外还填成未来，自动补全会把结束时间对齐到开始时间，避免出现负数用时。
* 重置一场比赛会一并清空开始 / 结束时间（计划时间保留）。

### 赛事（届）时间

`EventInfo` 有 `startTime`、`endTime` 与 `status`（`draft` 筹备中 / `active` 进行中 / `closed` 已结束）：

| 状态 | 条件 |
| --- | --- |
| 已结束 | 登记了结束时间，或届状态为 `已结束` |
| 进行中 | 其余情况；**赛程已经全部打完时不再显示「未开赛」** |
| 未开赛 | 开赛时间晚于当前时间且还没有已结算对局 |
| 筹备中 | 届状态为筹备中且还没有已结算对局 |

显示位置：顶栏时间芯片（`已结束 · 10/03 20:00 → 23:00`）、总览顶部的时间条（状态 + 开始 / 结束 / 用时 + 赛程进度）、
主页 / 全部赛事的卡片与只读查看页。**赛程打完但还没登记结束时间**时，总览会提示管理员去登记。

管理端 →「赛事信息」可设置起止时间与届状态，并带「开始时间=现在 / 结束时间=现在 / 清空结束时间」快捷键。
收尾时点一下即可，不必手打时间。

对应接口：

| 接口 | 说明 |
| --- | --- |
| `POST /api/rounds/{ref}/times` | `{scheduledAt, startedAt, finishedAt}`；字段缺省 = 不改动，空串 = 清空 |
| `POST /api/rounds/{ref}/result` | 除比分外可带 `{startedAt, finishedAt}`；缺省则沿用 / 用当前时间补全 |
| `PUT /api/config` | `{event: {startTime, endTime, status}}`，时间统一校验并规整为秒级 |

时间一律以**本地无时区**的 ISO 字符串存储（`2026-10-03T20:05:00`），前端 `new Date(...)` 直接按本地时间解析，
不会出现时区串位；输入同时接受 `2026-10-03 20:00`、`2026-10-03T20:00` 等写法，存储时统一归一化。

## 开赛锁定与替补

比赛一旦开始，**赛制与参赛人员就不能再动**——名单在赛前定稿，赛中只允许换人。

### 开始比赛（二次确认）

管理端 →「比赛状态」面板点「开始比赛」，弹窗里会列出当前准备情况
（赛制 / 参与选手数 / 队伍数 / 赛程场数，缺件会有提醒），**必须勾选「我已确认参与名单与赛制无误」**
按钮才会变成可点；服务端也要求 `confirm: true`，两边各拦一道。

开始后冻结的东西：

| 被冻结 | 为什么 |
| --- | --- |
| 赛制切换 | 换赛制会清空整个赛程 |
| 每队人数 / 每场同场队伍数 / 败者组开关 | 属于赛制参数 |
| 参赛名单 | 参赛人员定稿 |
| 随机组队 / 组队台 / 队伍成员 | 会重建队伍、清空赛程 |
| 生成 / 重建 / 清空赛程 | 会覆盖对局与比分 |
| 删除选手 | 名单只增不减 |

**仍然照常可用**：查看 / 复制**直播地址**（推流与播放）、**对局替补 / 队伍换人**、录分与重置、
时间登记、弃权、赛事信息（标题 / 场地 / 起止时间 / 届状态）、**直播本身**（没有总开关，
有赛事就能播）、**新增与编辑选手档案**（替上的人可能是个全新的人，得先建档）。

被冻结的接口统一返回 **409** 与一句说明；界面上对应的面板会被整体置灰（`<fieldset disabled>`
+ `pointer-events: none`），顶部「比赛状态」面板里写明「已冻结 / 仍然可用」两张清单。

### 对局替补（仅积分制）

**替补不是「选手的一种类别」**：名单里没有替补席，谁上场由**某一场比赛**决定。
在赛程里点某位在场选手即可安排替补，三档范围：

| 范围 | 影响 |
| --- | --- |
| 仅当前比赛 | 只换这一场（下一场回到轮换排定的阵容） |
| 本场及之后 | 从这一场起，之后每场都换成替补 |
| 全场 | 本届所有比赛都换（等于「他换人」） |

规矩（都在服务端执行）：

* **已结算的对局永不改写**：打完的比赛保留当时实际出场的阵容与比分，接口会把它列在 `lockedRounds`；
* **同场不撞人**：替补已经在那场阵容里时跳过该场（列在 `conflictRounds`），不会出现「同一个人两边都是他」；
* **同一选手 + 同一范围只有一处替补**：再指定一次就是**改人**，页面上只保留最后一次；
* **可随时取消**（总览 →「本届替补」或替补弹窗里），未结算的对局换回原主，已结算的照旧；
* 替补不在本届参与名单里时**自动加入名单**（接口回 `addedToParticipants`）。

关键在于**阵容是当场改写的**（不是渲染时才套用）：积分榜、场次与净胜分都按对局阵容统计，
所以「页面显示的人」和「榜上统计的人」永远是同一批人。想看「原来是谁」，页面上会同时标注
`甲 → 乙（仅当前比赛）`。

锦标赛制**没有**对局替补：固定队伍全程不换人，缺人只能判弃权，或整体换人。

### 队伍换人（固定队伍）

「比赛状态」或「组队台」→ **队伍换人**（`POST /api/teams/{team_id}/substitute`）：
队伍内 1:1 换人（`fromId` → `toId`），队伍规模不变，所以：

* **不重建赛程**，既有对阵结构全部有效；
* 该队**未结算**的对局出场阵容同步成新阵容；
* **已结算的对局保留当时实际出场的阵容与比分**。

换上的两条路径都会在**替上的人不在本届参与名单里时自动加入名单**，因此替补不必事先出现在任何名单中。

### 解除锁定

「比赛状态」→「解除锁定」同样需要二次确认（可填原因，会写进日志）。
解除后重新开放上述所有结构性调整；**已录入的比分不会被清除**，
但结构性改动按原有规则会让相关对局作废重来。

接口：`POST /api/event/start`、`POST /api/event/unlock`（都要 `{confirm: true}`）。

## 多届赛事

每一届赛事有独立名称、名单、队伍、赛程与成绩，全部存于同一个 SQLite 库中。
**没有「主赛事」**：主页列出全部届次，谁都不特殊、没有高亮、也没有「设为主赛事」。

### 主页（`/`）：唯一总入口

根路径就是一个**总览页**（不再是某一届）：

* 顶部是服务站名（**站点名称**，服务器管理员在「服务器 → 站点」设定）+ 三个统计
  （届数 / 进行中 / 直播间在播）；
* **全部届次按状态分组**：进行中 → 筹备中 → 已结束（分组顺序即优先级），
  **每组可折叠**（折叠状态记在页面会话里）、顶部**可搜索**（名称 / 编号 / 简介 / 榜首）；
* 两张**入口卡**：**频道**（进 `/channels`，任何访客都能看）与
  **管理赛事**（进 `/events`，**只对有赛事管理权限的人出现**）；
* 卡片上直接印着该届链接（`/e002`），可收藏、可分享。

### 页签规则：赛事与频道之间不互跳

页签只有两类，分界线就是「当前是不是在看某一届」：

| 当前路由 | 页签 |
| --- | --- |
| **赛事页**（`/e001…`） | **主页** · 总览 · 赛程 · 选手 · 直播（· 赛事管理，有权限时） |
| **其它**（`/`、`/channels`、`/events`、`/user`、`/admin`、错误页） | 只有 **主页** |

也就是说：**只能通过主页进入赛事或频道，赛事和频道之间不能直接切换**；
主页整条页签栏是收起来的（它自己就是总入口）。

### URL 路由

| 地址 | 看到什么 |
| --- | --- |
| `/` | **主页**：全部届次（按状态分组 · 可折叠 · 可搜索）+ 频道入口 |
| `/<届 ID>`（如 `/e002`） | 那一届的总览；`/<届 ID>/schedule`、`/roster`、`/live`、`/manage` 同理 |
| `/channels` | **频道**（独立路由，与届次无关）：成员直播间 + 传统频道，可切线路播放 |
| `/channels/<推流 ID>` | 直接打开那一路直播间（**第二段是推流 ID / 流名**，不是届次）；在页面里换台会自动用 `replaceState` 更新地址，于是刷新 / 收藏 / 分享掉的就是当前这一路 |
| `/events` | **全部赛事**（独立路由，**需要赛事管理权限**）：同一套分组板 + 管理操作（新建 / 重命名 / 封存 / 隐藏 / 删除）；访客与普通成员访问会看到错误页 |
| `/admin` | **服务器管理**（独立路由；仅服务器管理员可见）：站点 / 成员 / 届次 / 备份 / 直播封禁 / 自定义 HTML |
| `/user` | **我的**（独立路由；任何登录用户可见）：个人资料、直播间名字、凭据轮换、封禁状态 |
| `/developer` | **开发者**（独立路由，公开）：作者信息与联系方式、开源许可要点、开源组件清单；页脚「开发者」进入。数据与「开源组件」弹窗同源（`app/credits.py`），换 QQ / 仓库地址只改那处 |

* 顶栏左侧：赛事页显示**那一届的名字**，其它页面显示**站点名称**；浏览器标签同理
  （赛事页是「届名 | 站点名」，其它页面就是站点名）。赛事页才显示
  「届名 · 赛制」「进行中 · 开始时间未登记」这些比赛芯片；
* **进入某届时若有那一届的管理权限，会自动把它切到后端「当前届」**——于是
  「打开哪一届就能改哪一届」。后端所有写接口都作用在「当前届」上（没有届次参数），
  这个指针只是实现细节，不再是「主赛事」这种用户概念；
* 没有权限（别人的届 / 未登录）时点进去是**只读查看**：所有管理入口自动收起，
  直播页签也不出现，并且忽略 WebSocket 推送（服务端推的是当前届）；
* 地址里的届 ID 不存在、或指向一个被隐藏的届时，会落到**错误页**（见下）。

### 错误页（403 / 404）

需要权限、或地址确实不对的入口不再「悄悄回落到别的页面」，而是给一屏说清楚的错误页
（**页签里只剩「主页」**，不给任何不该有的入口；地址栏保持原样，方便把链接发给管理员看）：

| 触发 | 内容 |
| --- | --- |
| `/events` 而你没有赛事管理权限 | 403 · 「全部赛事」只对赛事管理员开放 |
| `/admin` 而不是服务器管理员 | 403 · 服务器管理仅限服务器管理员 |
| `/<届>/manage` 而没有管理权限 | 403 · 没有赛事管理权限 |
| `/<届>/manage` 指向**别人的届** | 403 · 这一届不归你管 |
| `/<届>` 指向不存在的届 | 404 · 没有这一届：xxx |

### 导航细节（真链接 / 滚动 / 过渡 / 触摸）

* **届次卡片与入口卡都是真链接**（`<a href="/e001">` + 拉伸覆盖整张卡）：整张卡可点，
  同时**中键 / ⌘+点击能开新标签页**、右键能**复制链接地址**、无 JS 时也还能用。
  路由只接管「左键普通点击」（`e.button===0` 且无修饰键），其余一律交给浏览器；
  卡片里的操作按钮（重命名 / 删除…）压在链接上面，不会被误当成跳转。
* **滚动位置**：新导航回顶部；**后退 / 前进回到那条记录当时的滚动位置**
  （`history.scrollRestoration='manual'`，滚动量记在各自的 history entry 里）。
  同一页只是刷新数据（保存后 `hooks.refreshState`）不会跳回顶部。
* **页面切换过渡**：用 View Transitions API 只让正文舞台淡入淡出，顶栏 / 底栏不参与；
  不支持的浏览器直接硬切，`prefers-reduced-motion` 下也自动关掉。
* **加载反馈**：点卡片后顶部出现**进度条**（不确定进度的滚动光带，最短显示 260ms，避免快得看不见），
  同时**被点的那张卡描边呼吸**；`goto` 带序号，途中又点了别的页面就直接放弃这一轮，
  先到的响应不会覆盖后点的那一页。
* **搜索词进地址**：主页 / 全部赛事页的搜索框写进 `?q=…`（`replaceState`，不新增历史），
  刷新、收藏、分享都还在；前进 / 后退也以地址栏为准。
* **触摸与窄屏**：
  * 输入框在窄屏（≤560px）字号提到 **16px** —— 否则 iOS Safari 一聚焦就自动放大整页；
  * 视口用 `dvh`（地址栏收起/展开不再让页面跳），弹窗高度同理；
  * 底栏每格最小 64px，六格放不下时**横向滚动**，不再把「赛事管理」挤成两行；
  * 触屏没有 hover：撤掉「浮起来」这类位移反馈，改用 `:active` 表达按压；
  * 触摸目标（页签）内边距加大到 ~44px 高；
  * 窄屏顶栏先让掉装饰性副标题（≤520px）与起止时间芯片（≤430px），保证「届名 + 按钮」不挤。

### 分享预览与 PWA

* **按路由注入标题 / og 标签**：`GET /`、`/e001`、`/channels`、`/admin`… 返回的 HTML 里
  `<title>` 与 `og:title` / `og:description` 都按这一屏算好（赛事页用「届名 | 站点名」+ 简介，
  隐藏的届只回站点名）。分享到 QQ / 微信时预览卡片因此是对的——
  抓取器不跑 JS，**只有服务端写对才算数**。基础 HTML 仍按资源版本号进程内缓存，
  标题是逐请求拼进去的，代价可忽略。
* **分享图（og:image）**：默认用内置那张 `/og.png`（1200×630，随站点 HUD 风格），
  同时带上 `og:site_name` / `og:url` / `og:locale` 与 `summary_large_image`
  （不带图时卡片只有一行字）。**og:image 必须是绝对地址**——所以它按请求的
  `Host` 拼出来，换域名不用改配置。想换成自己的图，在「服务器 → 界面配置 → 分享图」里
  填 `/static/xxx.png` 或完整网址即可（只收站内路径与 http(s)，其它协议一律丢弃）。
  内置那张可以用脚本重画：

  ```bash
  uv run python tools/make_share_card.py --title "异环赛事" --tagline "S2 · 秋季赛"
  ```

  产物 `static/og.png` 入库，改主色后重跑一次就行（Pillow 本来就在运行依赖里，
  见「图片推送：比赛卡片」——这个脚本不需要额外装什么）。
* **PWA**：`static/manifest.webmanifest`（`display: standalone` + 主题色 + 图标），
  `<link rel="manifest">` 已挂上；服务端给 `.webmanifest` 注册了 `application/manifest+json`。
  加到手机桌面后是全屏无地址栏的观感。

* **全部赛事页（`/events`）→ 卡片操作**：重命名 / 标记结束 / 恢复进行 / 隐藏 / 删除
  （只看得到自己创建的届，服务器管理员放行任意届）
* **服务器管理页（`/admin`）→ 届次管理**：全部届次的添加 / 关闭 / **隐藏** / 重命名 / 删除，
  并显示每届的**举办者名字**（赛事管理员只能管自己创建的届；见「成员、权限与服务器管理」）
* 新建届时可沿用当前届的选手与参与名单；队伍与赛程按新一届的名单重新随机生成
* 旧版 `config/events/*.json` 与 `config/match.json` 会在首次启动时**自动迁移**，
  原文件归档到 `config/migrated-json/`（可安全删除）

## 界面与观感

### 主题色（预设 + 自定义）

「服务器 → 界面配置 → 主题色」有 5 个预设（青 / 紫 / 品红 / 琥珀 / 青柠），**按届生效**——
换一届可以换一套配色。想要品牌色就填「自定义主题色」，收 `#rgb` / `#rrggbb`
（可省 `#`）：主色直接覆盖 `--accent`，副色（`--accent-2`）按色相 +40° 自动推出来，
所以只需要填一个值。**主题色会跟着进手机浏览器的地址栏配色**（`theme-color`）。

不认识的色值一律置空回落预设——CSS 里塞进垃圾值只会静默失效，不如在模型层挡住。

### 三步开赛（新装引导）

主页上有一张引导卡，只给**有管赛事权限的人**看，而且**缺哪步才说哪步**：
站点名称还是出厂值 → 催改名；直播开着但没填地址 → 催填；还没有届次 / 选手 → 给入口。
全部满足后自己消失，不想看可以点「不再提示」（记在本机 localStorage）。

刻意不做成弹窗或遮罩——那会挡住首页；它就是一张普通卡片。

### 比赛计时器

「正在进行」的每一场都带一块秒表（开始 / 暂停 / 归零），现场主持、裁判掐时间用。
它**不进后端、也不进赛制**：赛制里没有「比赛时长」这个字段，也不该有——
不同项目、不同赛制的时长没有可比性。所以状态存在本机（按对局编号各记一份），
刷新页面不丢，换台设备当然看不到——它就是块秒表。

### 图标与品牌标记

全站图标取自 **Feather Icons**（MIT，<https://feathericons.com>）——一套开放的
24×24 / 2px 描边图标集，共用一个 `static/js/icons.js` 表：

* 全部 `stroke="currentColor"`，所以**跟着主题色走**（含管理员自定义主题色）；
* 尺寸由容器字号决定，只有按钮 / 底栏 / 面板头 / 首页入口这几处按容器给定尺寸；
* 静态 HTML 写 `<span class="ic" data-icon="bell"></span>`，启动时由 `hydrateIcons()`
  补成内联 SVG；JS 模板直接 `icon('bell')`；
* **面板标题的图标按关键词自动挑**（`panelIcon()`，如「通知 / 公告 → 铃铛」），
  所以新增面板不用逐处配图标；认不出来时用品牌六边形兜底；
* 顶栏品牌标记与 `static/favicon.svg` 是同一套几何（六边形 + 准星），
  页面里那枚的渐变走主题变量，换主题色会跟着变。

不引图标字体 / 雪碧图：本站没有构建步骤，几十个图标内联一共十几 KB，
省掉一次请求，也没有字形加载闪烁。写错的图标名由 `tools/check_assets.py` 拦住
（否则只会「静静少一个图标」，不报错）。

### 弹窗的开关动画

全站只有一个弹层宿主（`#modal`），所有弹窗——Markdown 编辑器、开源组件清单、赛事通知、
成员编辑、确认框——都走 `core.js` 里的 `Modal`，所以**动画只实现一处**，新弹窗自动继承：

* 入场 200ms：背板淡入，面板从下方 12px 浮上来并放大 0.985 → 1；
* 出场 130ms（比入场短）：关窗是「这件事做完了」，不该让人等动画；
* 关键在 CSS 的 `@starting-style`：元素从 `display:none` 变可见时浏览器本来没有
  「起点」可插值，动画会退化成瞬间出现；它专门声明这种「首次显示」的起始状态。
  JS 那边还会再强制一次布局（读 `offsetWidth`）作为第二道保险——注意**不能**用
  `requestAnimationFrame` 代替：它的回调在本帧绘制之前跑，照样会被合并掉；
* `prefers-reduced-motion: reduce` 时只保留 80ms 的极短淡入，不做位移与缩放。

### 空状态与错误页

空状态是一枚跟随主题色的 HUD 图案（六边形 + 准星，用 CSS 遮罩 + 渐变实现，
换主题色 / 自定义色都会自动跟着变），403 / 404 页同样有一张「锁住的门」的插画。
文字层级也做过一轮校准：字段标签、说明文字、三级文字在深色面板上的对比度
都过 4.5:1，面板比底色亮一档并带一道顶部高光，卡片能从底色里浮出来。

## 通知与图文信息（Markdown）

公告、赛事信息、服务器信息都用**同一套 Markdown 编辑器**（悬浮大窗，桌面两栏、
移动端「编辑 / 预览」切换）：

| 内容 | 谁能发 | 展示在哪 | 赛后 |
| --- | --- | --- | --- |
| **赛事通知** | 赛事管理员（自己那届）/ 服务器管理员 | 打开该届时**自动弹窗**；历史在该届总览与「赛事管理」里 | **仍可发** |
| **服务器通知** | 仅服务器管理员 | 打开**任何路由**都自动弹窗；历史在主页 | 仍可发 |
| **赛事信息** | 赛事管理员（自己那届） | 用户端「比赛规则」面板末尾 | **只读** |
| **服务器信息** | 仅服务器管理员 | 主页底部「关于本站」 | — |

* **赛事信息（出厂为空）**：规则主体已经由「比赛规则」面板按赛制自动生成，
  这里只写组织者想补充的话（参赛须知 / 场地位置 / 注意事项）；**预填一段通则反而有害**
  ——改了赛制之后它就成了一句假话；
* **四类内容共用同一套 Markdown 编辑器**（通知 / 赛事信息 / 服务器信息），
  保存并关闭后**当页立刻刷新出渲染结果**，不必等广播或手动刷新；
* **删除要确认**：通知没有回收站，删掉之后打开站点的所有人都看不到它了，
  所以列表里的「删除」会先问一句；
* **改完立刻可见**：发布 / 编辑 / 删除之后，前端会把当前页面与管理面板一起重绘，
  通知面板同步换成最新内容——不必等下一次 WebSocket 广播，也不会出现「保存了但界面没变」；
  通知面板按 **id 现查宿主**，所以整页重绘后也不会往一个已经不在页面上的旧容器里写内容；
* **可以顺带推到 QQ 群**（编辑器的「同时发到 QQ 群」勾选，仅当群推送确实就绪时才出现）：
  群里收到的是**标题 + 摘要 + 站点链接**——通知可能是两万字，全推会把群刷成一屏；
  正文会转成纯文本（群不认 Markdown）并截断，末尾一句指向站内完整内容。
  **推不出去不影响发布**：通知已经存好了，失败只提示一句原因（要真报成失败，管理员会重发，
  站点里就多一条重复通知）；推群与「推送到群」**共用同一套限流**，也不 @ 人
  ——@ 人是 `比赛召集` 的活；
* **弹窗的「已读」记在本机**（localStorage）：看过并关掉就不再弹；**通知被修改后会再弹一次**
  （``id + updatedAt`` 做键），因为那正是它该被重看的场景。谁看过哪条通知不值得建表存；
* **正文按需再取**：状态广播里只有「最新一条的 id / 标题 / 时间」，正文只在真要展示时拉取——
  免得每次改比分都把公告重发一遍给所有在线客户端；
* 列表是**卡片 + 分页**（每页 4 条）：标题、时间、摘要（超出用省略号隐去），
  管理端多出「发布 / 编辑 / 删除」；
* 已结束的届：赛事信息只读（服务端拒绝改），**通知照发**——赛后公示成绩正好用得上。

### Markdown 支持范围

| 语法 | 效果 |
| --- | --- |
| `#` ~ `######` | 标题（工具栏给了 H1~H4） |
| `**粗**` `*斜*` `~~删~~` `` `码` `` | 行内强调 |
| `> 引用` / `- 列表` / `1. 列表` | 引用与列表（两个空格缩进可嵌套） |
| `\| 表格 \|` + `\|---\|` | 表格 |
| `[文字](链接)` / `![说明](图片)` | 链接与图片 |
| `---` | 分隔线 |

工具栏按钮**全部是内联 SVG 图标**（Feather Icons，MIT），用 `currentColor` 着色，
所以换主题色 / 自定义主题色都会跟着变。快捷键：`Ctrl/⌘+B`、`+I`、`+K`、`+S`。
代码块、裸链接、行内代码也都认；段落里的单个换行就是换行（写公告的人不会为换行敲两个空格）。

### 图片：上传与尺寸

* 编辑器里点图片按钮选本地文件 → 前端读成 data:URL → `POST /api/media` → 插入
  `![名字](/api/media/xxxx.png =100%)`；
* **点预览里的图片**可以调宽度：25% / 50% / 75% / 100% / 原始；语法是
  `=320`（宽）、`=320x180`、`=50%` 三种，渲染成 `width` / `height` 或 `style="width:50%"`；
* 服务端**按魔数判断真实格式**（不信 data:URL 里声明的 MIME），只收 PNG / JPEG / WebP / GIF，
  **不收 SVG**（SVG 能带脚本，属于「看着像图片的可执行文件」）；单张上限 8 MB；
* 文件名就是内容哈希：天然去重、不可能路径穿越，也就能放心发一年期 immutable 缓存。

### 同一张图只存一份（去重）

**所有**上传图片都进同一个内容仓库（`data/uploads/`，`app/media.py`）：通知 / 赛事信息里的
插图走 `POST /api/media`、头像走 `POST /api/avatar/upload`，但落盘是同一段代码，所以

* 同一张图**从哪个入口传、传几次，磁盘上只有一份**——第二次直接复用已存的那份，
  返回的还是同一个地址；
* 客户端把 MIME 写得再离谱也不影响（一张 PNG 声明成 `image/jpeg` 也只会有一个文件：
  格式由**魔数**决定，扩展名与内容一致）；
* 判定是**逐字节比对**内容哈希命名的候选文件，不是「只信文件名」；万一哈希撞名或
  文件被人改过，会退到完整哈希命名，**绝不覆盖别人的图**；
* 读取时的 MIME 也**按内容**给（历史文件里扩展名可能与内容不符，按扩展名发 MIME
  会让浏览器拿到「自称 JPEG 的 PNG」）；
* 升级前的老数据由**一次性收拢**处理：原本放在 `data/avatars/` 的本地头像在启动时并进
  统一仓库（同名同内容 → 删掉多出来的那份），头像是从旧地址 `/api/avatar/file/<名字>`
  引用的，所以**那个地址照旧保留、老资料不会失效**；
* **已经部署的服务器不用做任何事**：收拢就在启动流程里（`app/main.py` 的 lifespan，是
  **等它跑完**再继续的——搬移途中若正好有备份在打包，会漏掉几张贴图），所以
  * 手动重启一次 = 收拢完成；
  * 走热更新（`git pull` / 管理端点「立即更新」）换代 = 新进程启动时自动收拢，服务全程不中断；
  * 收拢是**幂等**的，且只认内容寻址的命名——手工丢进那个目录的文件一律不碰；
* 管理端「服务器信息」里的「上传图片」统计的就是这个仓库（含本地头像），
  另有 `legacy` 一项显示「旧目录里还剩几个没并进来」（正常是 0）。

### 为什么 Markdown 由服务端渲染

编辑器预览与发布走的是**同一个渲染器**（`POST /api/md/preview`），所以「预览什么样、
发布就什么样」，也不会出现两端渲染不一致这种最难查的问题。渲染器是自写的受限子集
（`app/markdown.py`），**先整体转义再做结构解析，不放行任何原始 HTML**——
否则赛事管理员就成了打向服务器管理员的 XSS 跳板（会话令牌就在浏览器里）。
链接只放行 http(s) / mailto / 站内相对路径，`javascript:` 与 `data:` 一律丢弃。

## 缓存策略

目标只有一句话：**该缓存的大文件长缓存，源文件一改浏览器立刻换新的**。

| 路径 | 策略 | 为什么安全 |
| --- | --- | --- |
| `/static/v/<版本号>/…`（首页注入的就是这个） | `immutable` 一年 | 版本号 = 全部静态文件的「路径 + 大小 + mtime」哈希，**文件一改 URL 就变** |
| `/static/…`（没带版本号，手输或旧收藏） | `no-cache` | 允许 304，但不许直接用旧副本；**不能让它按启发式规则自己缓存** |
| `/api/media/<哈希>` 与 `/api/avatar/file/<哈希>`（上传的图片，含本地头像） | `immutable` **一年** + `nosniff` | 文件名就是内容哈希，改图 = 换文件名；两条地址是**同一张图**，共用一份头（`media.IMMUTABLE_HEADERS`），免得「换个地址访问行为就变」 |
| `/api/cards/<哈希>.png`（比赛卡片） | `immutable` 一年 | 同理：内容定址，换内容就是换文件名（只认签发过的哈希） |
| `/api/avatar/p\|m\|c/<id>`（服务端代理的 QQ 头像） | 1 小时 + `stale-while-revalidate=86400`；`?refresh=1` 时 `no-store` | **不能**长缓存：QQ 那边换头像要能跟上（服务端磁盘缓存 12 小时）；点「刷新头像」走的就是那个 `no-store` 的地址 |
| `/og.png`、`/help.jpg` | og 十分钟 / help `no-cache` | 分享图与机器人帮助图：路径短、**不随资源版本号变**，换图不用改任何引用 |
| `/api/…` 其它接口 | `no-store` | 数据类响应一律不缓存 |
| `/`（HTML） | `no-store` | 每次拿到最新的版本号；标题与 og 标签也要按路由现拼 |

因此**改了 JS / CSS / 图片，都不需要手动清缓存**，也不需要重启进程：刷新页面就是新的
（前端模块之间是相对导入，会一并走到版本化路径下）。

## 安全清单（对外提供服务前）

这个项目出厂是「局域网自用」的配置，公网部署前请逐条确认：

| 检查 | 为什么 | 怎么做 |
| --- | --- | --- |
| **保管好服务器管理员密钥** | 它是全站最高权限的唯一入口（成员密钥登录，没有旁路） | 首次启动时日志里那份密钥**只出现一次**，抄进密码管理器；丢了就在服务器上执行 `--reset-key` 重置（见「登录与权限」）。不放心的话在 `config/` 目录权限上也收一道 |
| 用 HTTPS 反代 | 会话令牌与推流凭据走明文会被中间人拿走；浏览器还会拦掉混合内容（直播播不了） | 反代终止 TLS，媒体服务器同样配证书 |
| `config/` `data/` `backups/` 不要外发 | 这三个目录里有成员凭据哈希、推流令牌与头像缓存 | 仓库 `.gitignore` 已排除它们，**别改成强制加入** |
| 会话令牌**只走请求头** | 查询串会原样进反代 / CDN 的访问日志，而且 `?token=…` 等于「一个链接就能改数据 / 下载整库」 | 已做到：会话只认 `X-NTE-Token`（`?token=` 一律 401，读写都一样）；导出 / 备份 / 旧数据快照的下载改成前端带请求头取回 blob 再另存（`core.downloadFile`）；自身访问日志默认关闭、操作日志只记路径不记查询串；会话 12 小时过期 |
| 机器人令牌只走请求头 | 它**不会过期**，而查询串会进日志 | 已做到：`/api/bot/*` 只接受 `Authorization` / `X-NTE-Token`，`?token=` 一律 401（有测试守着） |
| 推流不接受匿名 | 否则谁都能推到你的流名上 | MediaMTX 侧配 `authHTTP` 指到本站 `/api/live/auth`（见「推流鉴权」） |
| 登录爆破 | 成员密钥本身是 192 位随机、猜不中，但登录接口仍会被持续试探，且「猜中某人 = 拿到他的权限」 | 已内置类 fail2ban（见「登录失败限制」），公网下建议保留默认阈值；不用的人及时停用成员 |
| **主直播间要设推流令牌** | 流名是**公开的**（观看地址 `…/<流名>/` 里本来就有），而留空令牌时「登记过的流名就能推」——等于谁都能顶掉主直播间 | 「直播配置 → 推流令牌」填一个；成员机位不受影响（那边本来就要求「推流 ID + 成员自己的令牌」） |
| 交互式接口文档 | `/api/docs`、`/redoc`、`/openapi.json` 会把全部接口与数据结构摊开 | **默认已关闭**；对接 / 调试时临时 `NTE_DOCS=1` |
| 比赛卡片图是公开的 | 它要发到群里给 QQ 客户端直接拉，没法带鉴权 | 文件名是**内容哈希**，且只认**推送 / 预览时签发过**的哈希（`card.resolve`）——没流出去的卡片读不到，也不是「换个链接就能下载点什么」；内容本身与推送到群里的信息一致 |
| 自定义 HTML | 「服务器 → 自定义 HTML」是**原样注入**（其中的 `<script>` 会执行），这是有意的（接统计代码），但它等价于把整站交给填它的人 | 只填自己信任的代码；该字段在界面上也标了「会执行其中的 `<script>`」 |

安全响应头由服务端统一补上（**保守一组**，且不与站内自定义 HTML / 头像 / 直播流冲突）：
`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、
`Content-Security-Policy: frame-ancestors 'self'`、`X-Frame-Options: SAMEORIGIN`、
`Permissions-Policy: geolocation=(), microphone=(), camera=(), payment=()`
（本站确实不用这些能力，声明「用不到」能挡住被注入脚本后的权限滥用）。

刻意**没有**加 `Strict-Transport-Security`：它只在 HTTPS 下有意义，而且一旦浏览器记住，
同域的 http 请求也会被强制升级——本地调试与内网部署会被它坑。

  运行依赖（含**可选**的 Pillow：装了才发卡片图，没装退回纯文本）、前端资源（Feather Icons）、
  外部程序（**MediaMTX**：独立部署、不随本站分发）、开发与 CI。

**许可证兼容性**：依赖全是宽松许可或弱著佐权（MIT / MIT-CMU / BSD-2 / BSD-3 / Apache-2.0 /
MPL-2.0 / PSF-2.0），**没有任何 GPL-only 组件**——只有那类会与 AGPL-3.0 冲突
（GPLv2-only 不能与 AGPLv3 组合；GPLv3 与 AGPLv3 是单向兼容）。
这条不只写在文档里，`tests/test_credits.py` 每次 CI 都查四件事：

1. `pyproject.toml` 声明的依赖都署名了；
2. **`uv.lock` 里实际会装的每一个包**都在清单里（含传递依赖——只对顶层声明是不够的，
   `annotated-doc` 这种就是跟着 FastAPI 进来的）；
3. 反向也查：清单里**没有已经不再安装的包**（`sniffio` 就是 anyio 4 之后被淘汰的，
   留在清单里会让人以为依赖它）；
4. 清单文本里**没有 Markdown 记号**（页脚是 `esc()` 纯文本渲染，写 `**粗体**` 只会显示星号）
   以及没有与 AGPL 冲突的许可、MediaMTX 没被漏掉。

换了依赖忘了署名、或引入 GPL-only 的包，CI 直接红。

> 为什么是 AGPL 而不是 MIT：这是**网络服务**。用 MIT 的话，别人改了挂起来对外提供，
> 你拿不到任何回馈；AGPL 只多要求「改了就公开」，不影响自用与二次开发。

## 部署与边缘缓存（德国源站 + EdgeOne）

源站带宽/延迟有限时，缓存策略比代码优化更关键。服务端已内置以下策略：

| 路径 | Cache-Control | 说明 |
| --- | --- | --- |
| `index.html`（`/`、SPA 回落） | `no-cache` | 始终回源校验；内容极小 |
| `/static/v/<hash>/**` | `public, max-age=31536000, immutable` | 资源带内容版本号，可放心长期缓存 |
| `/api/**`（默认） | `no-store` | 动态状态，禁止边缘缓存（下面两条图片路径会显式覆盖它） |
| `/api/media/<哈希>`、`/api/avatar/file/<哈希>` | `public, max-age=31536000, immutable` | 上传的图片（含本地头像）：内容寻址，换图 = 换文件名，可长期缓存 |
| `/api/avatar/p\|m\|c/<id>` | `public, max-age=3600, stale-while-revalidate=86400` | 服务端代理的 QQ 头像：**不能长缓存**（人家换头像要跟上）；`?refresh=1` 时 `no-store` |
| `/help.jpg` | `no-cache` | 机器人帮助图：**别在边缘长缓存**，换图后群里要立刻看到新的 |

其中 `<hash>` 由 `static/` 目录的路径/大小/mtime 计算，**任何静态文件改动都会自动换新 URL**；
`index.html` 在输出时被注入当前版本号，因此不需要手工改引用。

EdgeOne 侧建议：

1. 缓存规则：默认 `遵循源站`，对 `/static/` 前缀可再叠加「忽略查询串 + 长 TTL」；
   确保 `/api/*` 为「不缓存」。
2. `/ws` 需放行 WebSocket（关闭缓冲），否则实时推送会失效。
3. 回源协议用 HTTP + Keep-Alive（源站已设 `timeout_keep_alive=30`）；TLS 由 EdgeOne 终结。
4. 压缩：源站已对 ≥1KB 响应启用 gzip，且 WebSocket 开启 per-message deflate；
   EdgeOne 若也开启压缩，注意避免重复压缩（`Vary: Accept-Encoding` 已设置）。
5. 运行时用**单进程**（`NTE_WORKERS=1`）：多进程下 WebSocket 广播不跨进程。
6. **跨域默认关闭**：前端由本站同源提供时无需任何 CORS 配置；仅当前端单独部署在
   别的域名时才用 `NTE_CORS_ORIGINS` 显式列出允许来源（不要用 `*`）。
7. 站点前面有 CDN / 反向代理时，记得在 `/admin → 登录限制` 里把**代理的 IP / CIDR**
   填进「可信反向代理」，否则登录失败限制只能看到代理 IP（管理端会显示解析到的客户端 IP 供核对）。

### 服务器上要装中文字体（卡片图 / 帮助图用它画中文）

卡片图与帮助图是服务器**用 Pillow 画**出来的，画中文必须有 CJK 字体（思源黑体就是
Google 那份 **Noto Sans CJK**）；没有的话图里的中文会变成方框。Docker 镜像里已经装好了
（`Dockerfile` 里 `apt-get install fonts-noto-cjk`），**裸机部署**要自己装一份：

| 发行版 | 命令 |
| --- | --- |
| Debian / Ubuntu | `sudo apt install -y fonts-noto-cjk` |
| RHEL / AlmaLinux / Rocky / Fedora | `sudo dnf install -y google-noto-sans-cjk-fonts` |
| Arch / Manjaro | `sudo pacman -S --noconfirm noto-fonts-cjk` |
| Alpine | `apk add --no-cache font-noto-cjk` |

装完**重启一次服务**最省事（启动时会用新字体重画帮助图；运行中装的字体也会被后来的
请求认出来，但已经用内置字体画过的那些卡片要等下次内容变化才重画）。自检三步：

```bash
fc-list | grep -i -E "noto.*cjk|source han"          # 系统认到了没
uv run python -c "from app import fonts; print(fonts.resolve('cjk'))"   # 本站找到哪一支
uv run python tools/make_help_card.py --out /tmp/help.jpg             # 出一张看看中文对不对
```

查找顺序是「环境变量 → 常见路径 → **扫字体目录**（按文件名认，发行版塞在哪一层都行）
→ 内置兜底」，所以多数情况下装完就能用；放在奇怪位置、或想指定某一支时直接点名：

```bash
NTE_FONT_CJK=/opt/fonts/SourceHanSansSC-Regular.otf uv run python -m app
```

（另有 `NTE_FONT_MONO`（卡片顶部编号用的西文）、`NTE_FONT_LATIN`（帮助图上的西文小标签）。）

想在容器里也用**热更新**（见上一节）：镜像里得有 `git`，启动命令换成守护
（`CMD ["uv", "run", "--no-sync", "python", "-m", "app", "hotrun"]`）——
零中断交接在 Linux 上是原生的。**不换也完全没问题**：容器重建=重启，
赛事数据在 `/data` 卷里，照样不丢。

**直播不进这个镜像**：本站只负责「谁在播 / 观看地址 / 远程掐断」，媒体服务器
（MediaMTX）是独立服务。`docker-compose.yml` 里留了一段注释掉的模板，
自建时接上来，再到「服务器管理 → 直播配置」填它的地址（WebRTC :8889 /
HLS :8888 / 控制 API :9997）。注意两点：WebRTC 走 UDP，用 host 网络最省事；
浏览器只允许在 HTTPS（或 localhost）下播放，所以**生产环境必须给媒体服务器配证书**。

> 出厂**不预填任何直播地址**。以前默认值指向某个具体域名，新装的人会「看起来配好了、
> 其实连的是别人的服务器」；现在留空，各处都会明确提示「未配置」，不会静默失败。

## 热更新（`git pull` 换代码，不中断服务）

比赛正在打的时候，重启一次 = 所有在线的人掉线一次。所以把「换代码」交给一个
**只持有监听端口的守护进程**——而且**默认就是它**：

```bash
uv run python -m app                    # 起服务（默认启用热更新守护）
uv run python -m app --interval 1       # 检测间隔（默认 2 秒）
uv run python -m app --no-hotrun        # 退回原始单进程启动（**没有热更新能力**）
uv run python -m app --check            # 只体检：代码能不能起来（不占端口、不碰数据库）
```

**启动自检与换代结果都会印在控制台，也会出现在「服务器 → 热更新」里**——同一份清单
两处显示，不用为了看一眼状态去翻日志：

```
====================================================================
热更新自检
  [OK ] 换代方式：零中断交接：父进程持有监听套接字，新老进程同时 accept，服务不空窗
  [OK ] 监听端口：0.0.0.0:8000 已由守护持有（子进程继承）
  [OK ] 代码仓库：当前提交 8d41f0c2，可以 git pull
  [OK ] 工作区：干净，可以自动 git pull
  [OK ] 新代码预检：python -m app --check 通过（每次换代前也会再跑一次）
====================================================================
```

三件事都做到，才叫「不中断」：

| 目标 | 靠什么 |
| --- | --- |
| **服务不空窗**（Linux） | 父进程持有监听套接字；换代时**先起新进程**、确认它真能收请求，再让旧进程优雅退出——两个子进程短暂地同时 accept 同一个套接字 |
| **登录不掉线** | 会话落库（`sessions` 表，存的是令牌的 sha256）：新进程内存里没有，但会去库里认一次 |
| **坏版本不上线** | 换代前先跑 `python -m app --check`（只导入、不起服务、不占端口）；起不来就**保持现状**，旧版本继续服务 |

换代怎么触发：**改代码保存**（守护每 2 秒比一次文件指纹与 HEAD）、`git pull`
（管理端「服务器 → 热更新 → 拉取更新并换代」）、或点「重新加载代码」。

`git pull` 有两条安全线：只跑 `--ff-only`（分叉了宁可报错，也不在服务器上留一个没人
看过的合并提交）；工作区**有未提交改动就拒绝**（自动 pull 覆盖别人正在改的文件，比
「不更新」糟得多）。`uv.lock` / `pyproject.toml` 变了会顺带 `uv sync --frozen`。

**前端一起换**：静态资源地址本来就带内容版本号（`/static/v/<哈希>/`），`git pull`
之后重新打开页面拿到的就是新代码；**已经开着的页面**会收到一条「站点已更新 ·
点此刷新」的提示（不强制刷新：人可能正在录入比分）。

每次换代结束后还有一段结论（控制台与前端同一份）：

```
====================================================================
热更新完成
  提交：8d41f0c2 → 1f7c9ab3
  触发：管理端请求（服务器管理员） · 方式：pull
  耗时：1.8s · 已换代 2 次
  git pull 已更新到 1f7c9ab3（12 个文件）；新进程已接管并确认能收请求，旧进程优雅退出（服务未中断）
====================================================================
```

失败时同样两处都会写清楚（`预检没过` / `git pull 被拒` / `新进程起不来`），并明确
「旧版本继续服务」还是「服务已停、需手动重启守护」——不让人靠猜。

> **平台差异说白**：Linux 上是**零中断**（上表第一条）。Windows 上跨进程移交监听
> 套接字只有「半个能用」——拿到的套接字看着在监听，却 accept 不到请求（实测），
> 所以那边自动退到**顺序换代**：先停旧进程、等端口放开再起新的，中间约 1 秒连不上。
> 本机开发够用，生产（Linux）不受影响。自己这台是哪种，管理端「服务器 → 热更新」
> 会写明「零中断交接 / 顺序换代」。
>
> **验证到什么程度**：`fd` 继承这条 OS 层的路在真实 Linux（AlmaLinux 9）上验过——
> 父进程 bind+listen、`pass_fds` 递给子进程，子进程在**继承来的套接字**上 accept 并
> 正常响应 ✓。再往上一层（asyncio 的 `create_server(sock=…)`，即 uvicorn 实际用的那个
> API）在这台 WSL 里验不了：它只有 Python 3.9，而本项目要求 ≥3.11，3.9 上这个 API
> 本身就是坏的（三种写法都收不到响应，与是否预先 listen 无关）。**上线后请在服务器的
> Python（≥3.11）上跑一次**：换代时盯着控制台那段结论，或 `while curl -s ...` 打一圈看
> 有没有失败——「服务未中断」这句话值得亲眼确认一次。

> 不用守护也照旧：`uv run python -m app` 起服务一切功能都在，只是**没有热更新能力**
> ——管理端会明确告诉你「不是由守护启动的」，不会出现「点了没反应」。

## 开发

```bash
uv sync --extra dev      # ruff / pytest 在 dev 可选依赖里，要先装（Pillow 是正式依赖，uv sync 就有）

uv run pytest            # 585 条：结算 / 计分口径 / 替补 / 旧数据升级 / 加固与出厂默认 / 规则文案 / 参赛名单 / B站 接入 / 比赛卡片与字体 / 图片段两条路（上传换 attachment_id）/ 直播常驻探测 / 热更新 / 封禁 IP / 备份还原 / 图片去重与缓存 / 终端彩色 / QQ 自助与推送 / 通知推群 / 校验 / 存储 / 接口 / 权限 / 凭据 / 推流鉴权 / 通知 / 版权 / 插件
uv run python tools/check_assets.py   # 前端静态资源自检（见下）

```

> Pillow 是**正式依赖**（图片推送与帮助图都靠它渲染），所以 `tools/` 里那两个出图脚本
> 也不需要 `--with pillow` 了——直接 `uv run python tools/...` 就行。

> 只跑 `uv sync` 的话不会装 ruff / pytest；`uv run ruff` 会报
> `Failed to spawn: ruff`，补一次 `uv sync --extra dev` 即可。

### 测试怎么写的

前端是原生 ESM、没有打包器，后端也没有类型检查，所以**测试就是唯一的门禁**：

* `tests/conftest.py` 第一件事是把 `NTE_DATA_DIR` 指到临时目录——整套测试
  **绝不会碰仓库里的 `config/nte.sqlite3`**（这是硬要求，别改成相对路径）；
* `test_settlement.py` 盯结算：四轮的大比分 / 总成绩、2:0 提前结束、大比分打平比总成绩、
  弃权、多队同场名次、并列要交回管理员；
* `test_validation.py` 盯提示文案：某一轮只填了一方、已分出胜负却没有成绩、人数不够、
  名单留空 = 全员参与；
* `test_storage.py` 盯数据库：新字段往返、**旧库自动补列**、退休的列会被清掉、
  操作日志只留最近 N 条、日志写失败必须被吞掉（它是观测手段，不能反过来把请求搞挂）；
* **`test_metric.py` 盯计分口径**：三种类型的解析与显示、小数按千分之一存、
  数值高胜的排序与改造前**逐项等价**（含并列）、数值低胜的方向、
  数值型的 `0` 是合法读数而时间型的 `0` 是「没有成绩」、哨兵不许当第一、
  `0:0` 是真平局而「两方都没填」不是、大比分是计数不许被当成时间、
  小组赛「完成场次 → 总成绩」；
  还专门构造了一个「净胜分与速度给出相反答案」的场景——那是唯一能证明
  「必须按判断标准分支」的用例；
* `test_subs.py` 盯对局替补：三档范围、**已结算的对局永不改写**、同场撞人跳过、
  改人只留最后一次、取消还原，以及「显式空名单 ≠ 未指定」；
* `test_legacy.py` 盯升级退路：**转换前先留旧库快照**（快照里必须是转换前的样子）、
  升级幂等、`score` → 自然数 + 得分 + 数值高胜、快照只读且没有还原接口；
* **`test_rules_text.py` 盯规则的「对错」**（不是好不好看）：配置 4 队同场而实际排出
  3 队同场时只说 3（不并列两个数字打架）、2 队同场说「组 vs 组」、单败的届里不许描述
  败者组怎么打、规则里不许出现「（完全确定，无随机）」这类旁白、
  网页那份 `**加粗**` 真的渲染成 `<strong>` 而纯文本那份一个记号都不留、
  拼进去的用户输入被转义、自动分组数随人数单调增多且每组不少于 3 队；
* **`test_console.py` 盯终端彩色**：只在真终端上色（管道 / 重定向 / 测试捕获里一个转义码
  都不许有）、`NO_COLOR` 一定生效、列宽按显示宽度算（汉字两列）、折行不会把
  `--delete-old` 这种命令从中间切开、收尾标点不跑到行首；
* **`test_media_dedup.py` 盯「同一张图只有一份」**：公告入口与头像入口互相复用、
  同一个字节把 MIME 写成别的也只会有一个文件（扩展名按魔数定）、不同的图各存各的、
  旧头像目录里的图**两个地址都读得到**且再上传会复用、历史重复由收拢删掉、
  非内容寻址的手工文件不碰、下载的 MIME 按内容给、备份带上这些图并能还原；
* **`test_backup.py` 盯「出事时要救命」的那条路**（平时没人跑，用的时候正好最慌）：
  备份 zip 里**确有**数据库快照与清单（不是空壳）、**还原真的能把数据倒回去**
  （改过的站点名回到备份那一刻）、还原前**自动打一份安全备份**、
  还原后**注销全部会话**（成员与凭据可能已回退，旧会话不该继续有效）、
  坏文件上传明确报错且**当前数据毫发无损**、备份名走白名单（`../` 一律拒）、
  以及旧数据快照能列能下载但**故意没有还原入口**；
* **`test_ip_bans.py` 盯封禁 IP**：人工封禁（临时 / 永久）与改时长、**人工封禁优先于白名单**
  （自动封禁仍尊重白名单）、非法 IP 被拒、过期记录自动从列表消失、
  搜索（IP 片段与原因文字）、四类过滤、分页（永久排最前、越界回空）、
  以及接口层的权限与错误码；
* **`test_hardening.py` 盯「不该发生的门」**：会话令牌**只认请求头**（`?token=` 读写都 401）、
  健康检查公开但不漏名单、保存队伍时空分组被丢弃（接口层兜底）、新届赛事信息出厂为空、
  直播没有总开关（硬塞 `enabled=false` 也关不掉）——这一组都不会报错、不会崩，
  只是安静地开着一扇门，所以只能靠测试守着；
* **`test_bili.py` 盯 B站 接入**（网络全部打桩，真实请求在 CI 里必然 flaky）：
  房间号的录入容错（粘链接 / 带文字都收、非数字要报错）、只有 `live_status==1` 才算在播、
  **开播后自动同步标题 / 主播 / 在线 / 分区 / 开播时间**、短号也要用真实房间号拼地址、
  探测结果被缓存、探测失败＝「不知道」而不是「没人播」、**房子不存在与探测失败分开**、
  保存房间号时当场校验（填错给提示但**绝不拦保存**）、房间号没变就不再打扰 B站、
  `collect_live` 里那一路带的是**播放器与跳转地址**（没有本站的推流 / 观看地址）、
  以及群里那条消息也能点到直播间并带上标题；
* `test_validation.py` 还盯**规则文案**：分组 / 每队场次 / 名次分表 / 出线名额 / 淘汰赛结构

  赛制一换整套跟着换；
* `test_metric_api.py` 盯链路：改配置 → 录入 → 状态（含排行与规则文案）真的串起来，

* **`test_markdown.py` 盯渲染器的安全边界**：`<script>` 只被当文字、`javascript:` 链接退化成

* `test_notices.py` 盯通知的权限与校验：赛事管理员只能碰自己那届、服务器通知只有服务器管理员

  图片响应的缓存头；
* `test_secrets.py` 盯**凭据不外泄**：把推流令牌 / MediaMTX 账密 / 机器人令牌真的写进配置，

* `test_credits.py` 盯许可证：**`uv.lock` 里实际会装的每个包**都署名了（含传递依赖）、

* **`test_permissions.py` 盯权限面**：把所有写接口（含 router 里的）连同依赖一起枚举出来，

  这类问题的表现是「不报错、不崩，只是安静地多出一个谁都能调的接口」，只能靠测试拦住；
* `test_live_auth.py` 盯推流鉴权：令牌只能推自己的流名、没令牌 / 没配令牌都不放行、

* **`test_live_watch.py` 盯常驻探测**：一直在探（异常 / 超时都只跳过这一轮，循环必须活下去）、
  **状态变了才广播**（同一种状态连探三轮只推一次）、失败后 2 秒重试而不是等空闲间隔、
  间隔按需放宽（没人播也没人在线才放宽，**不是停**）、`kick_refresh` 在缓存新鲜时不再多打一轮、

* `test_stream_keys.py` 盯推流标识与令牌**只收 ASCII**（含全角 / emoji / 空格）；
* **`test_roster_members.py` 盯「名单从成员列表来」**：候选列出**全部成员**（含本届还没档案的、

  这组**自己新建一届**再跑（`_own_event`）：参与名单是「每届一份」，而单场需要几个人由
  赛制决定（`每队人数 × 2`）——别的用例把当前届改得带赛程之后，再勾一位成员就会触发
  「按名单重排未结算对局」，撞出「可用选手 1 人，少于单场所需的 4 人」这种与本题无关的 400
  （也就是「单独跑绿、全量跑红」）；
* **`test_fonts.py` 盯字体查找**：四层查找（环境变量 / 常见路径 / 扫字体目录 / 内置兜底）、
  「没找到」不缓存（运行中装上字体也能认出来）、坏字体文件不崩；
* **`test_card.py` 盯比赛卡片**：内容跟着赛制走（组 vs 组 / 三队 / 四队同场各一套说法、
  规则来自 `logic.rulebook` 同一份）、同样内容指纹不变而改赛制就变、**同一份内容只渲染一次**、
  画出来是真能打开的 PNG、没装 Pillow 或渲染炸了都安静退回文本、`/api/cards/<hash>.png`
  **只认签发过的哈希**（凑出来的地址 404）；顺带盯文本里的**规则摘要**（不带 Markdown、
  会按上限截断）；
* **`test_bot_profile.py` 盯 QQ 自助**：新建成员发一次「比赛直播注册」就拿到推流码 + 令牌 +
  地址 + 注意事项（令牌能对上库里的哈希）、**已有推流码的人令牌一动不动**、
  「有推流码没令牌」补一把、管理员 @ 代办时**私聊仍发给那个人**、非管理员代办 403、
  私聊发不出去时令牌**绝不进群**；游戏 UUID 群内可查且不需要权限；资料的每一项与改法都在，
  改一项只动那一项、推流码与 QQ 走唯一性、写「清空」才清空、未知字段要报出可用写法；
* **`test_qqbot_push.py` 盯推送链路**：图片段的字段名逐个试（400 才换下一个，500 直接放弃）、
  **老形态被拒（`image part missing attachment_id`）后自动上传换 id 再发**、
  上传的 multipart 字段名逐个试、`attachment_id` 在响应任意层级都能挖出来、
  **成功一次就记住那条路**（第二次不再白撞三次 400）、缺 `file` 权限的 403 说清去哪儿勾、
  传上去了却没拿到 id 就把响应原文带出来、老版本直接吃地址时**不做多余的上传**、
  四道前置检查、有图时 `比赛信息` 的正文只留一行、`详情` 保留全文、
  **图发不出去就退回完整文本（带规则）**、进度类不生成卡片、预览只回不发的 `card` / `cardText`、
  **关掉「图片推送」开关后连图都不画**、推送时**把卡片字节一起交出去**（缓存命中就从磁盘读），
  以及「测试发图」会回报实际生效的那条路；
* **`test_notice_push.py` 盯通知顺带推群**：只推摘要 + 站点链接（两万字的通知不会刷屏）、
  正文里的 Markdown 记号被去掉、**推不出去也照旧发布成功**（只回一句原因）、
  被限流时把「还要等几秒」一起回给前端、改完通知也能再推一次；
* **`test_hot.py` 盯热更新**（大部分是纯逻辑，最后一条**真的拉起守护与业务进程换一次代**）：
  控制文件的读写与「取出即消费」、就绪文件带着**真实 pid**、自查口的口令校验
  （没口令与「没这个路由」不可区分）、没开守护时**明确报错而不是假装成功**、
  预检拦下坏版本、文件指纹忽略 `__pycache__` 与运行期产物、
  **默认启动就是守护**（四条逃生路各自回得去：`--no-hotrun` / `NTE_HOT=0` /
  自己就是子进程 / uvicorn 自己的 reloader）、启动自检把该点的名都点到、
  换代结果（`lastReload`）与业务进程回报（`app`）都能读到、
  **换代后新进程仍然认得旧令牌**（会话落库的全部意义）、
  以及那次真换代后「服务照常 + 登录没掉 + 结果被记下」。
  还有一条**孤儿用例**：把守护**硬杀**（不给它清理机会）之后，业务子进程必须自己
  让出端口——不然后台会留一个「占着端口的孤儿」，下次启动绑不上，看着像灵异事件。
  要跳过这两条慢用例：`NTE_SKIP_SLOW=1`；
* `test_plugin_helpers.py` 盯**插件的框架约定**（站点环境里没有 `astrbot` 包，所以先打桩再按路径
  加载插件模块）：命令参数不能声明成 `int`（框架会强转并抛异常、整条命令失效）、配置不能
  在构造时读死、报名/帮助图等纯函数的行为，以及三条新命令的**群内 / 私聊分寸**
  （UUID 群内回、资料与直播注册只私聊给本人、`_stream_key_arg` 要能剔掉 @ 带进来的 QQ）；
  另外钉住两条**风格底线**——插件里**不许出现
  `llm_tool`**（本项目不用大模型，答案要可复现），以及 `HELP_TEXT`（群里回的文本）、
  `HELP.md`（帮助图说明）与 `tools/help_card_content.py`（帮助图上真正印的字）
  **三处的命令集合必须一致**（这几处最容易漂移：图上的命令错一个字，群友照着打就没反应）；
* `tools/check_assets.py` 补前端：CSS 括号配平、相对导入是否存在、
  **导入的符号真的被导出**（`import { foo }` 而对方没有 `foo` —— 这类错没有任何静态检查
  兜着，只有在浏览器里点开那个页面才会白屏）、**图标名真的存在**
  （写错只会「静静少一个图标」，不报错）、`index.html` 引用的资源是否存在、
  **路由不会被页签回落踩掉**、**帮助图（若本地有一份）不比它的文案旧**、以及
  **帮助图文案里没有 Markdown 记号**（图只会画字，`**加粗**` 会原样印出星号；
  图不入库，服务启动时自动重画，指纹在 `static/help.jpg.src.sha256`）
  ——**没有打包器，这几类错只能靠脚本抓**。

CI（`.github/workflows/ci.yml`）在每次 push / PR 上跑 ruff、pytest、前端语法
（`node --check`）、静态资源自检，并构建一次镜像。
